# AIMatterLab 工具接入

与软件开发者协作，在指定工作空间生成 `工具名-package`。包内保留原软件的 Git 仓库，并在原仓库之外生成交付 skill 和测试重定向入口。`工具名` 为占位名称，不指某个特定软件。

本 skill 是接入指导，产出的包根 `SKILL.md` 是指导后续 Agent 安装、使用和测试该工具的交付 skill。接入判据仍为：五项工具定义齐备，能够完成安装并通过测试用例。`tool.json` v1 已有定义检查和版本快照注册；其 `definition_checked` 只说明定义与文件闭包通过检查，不代表安装、测试、接入或用户配置通过。

工具接入面向开发者，验证工具在声明流程中的可用性。工具配置面向用户，在其真实环境中安装、配置、测试后生成执行 skill；本接入流程不预造用户环境的执行 skill 或配置通过结果。

涉及力场与 MD 引擎、增强采样与 MD 引擎，或其他工具间接口时，必须阅读 [联用接口与运行环境交付](references/runtime-composition.md)。从实际实现枚举支持的接口和加载模式，区分产物交接、同进程调用及运行时通信，交付依赖约束、操作指导和最小联合用例。开发者负责接口事实，AIMatterLab 负责用户所选完整工具组的兼容环境配置和联合验收；两者不能用单工具安装成功相互替代。

编写交付材料时，阅读 [交付指南](references/deliverables.md)；生成 `tool.json` 或准备注册、更新时再阅读 [注册与版本契约](references/registration.md)。随本目录附有完整 schema 和纯声明检查器，不需要取得 AIMatterLab 源码才能理解字段、默认值和额外约束。包外层约定不约束原仓库内部布局。AimLab 内部声明也自包含：所需的 schema、纯声明校验器和引擎契约随本目录分发（`references/tool-package.schema.json`、`references/aimlab-tools.mjs`、`references/engine-contracts.json`），引擎契约是内部声明的唯一生产事实来源，编写声明不需要访问 AIMatterLab 源码。

AimLab 内部工具（例如 GPU-Sampling）不使用本 skill 的 `<id>-package` 交付形态，而是在工具仓库主工作分支维护 `aimlab-tools/` 声明，由 AIMatterLab 按候选 commit 执行接入检查。生成或更新 `aimlab-tools/` 时只允许修改工具仓库的 `aimlab-tools/` 目录，工具仓库其他文件保持既有默认分支内容不变；声明必须自包含，`manifest.id` 必须等于所声明引擎的 `aimlab_tool_id`，生产 token 必须覆盖契约的 `declaration_tokens`。仓库内文件夹要求、`manifest.json` 字段与生产 token、测试要求、检查命令和状态见 [AimLab 内部工具约定](references/aimlab-tools.md)；第三方开发者可忽略本段。

## 明确软件和功能范围

读取目标仓库的开发约束、源代码、公开接口、安装说明及已有测试，确认实际版本、Git 提交和本次接入范围。记录已有接口、文档、测试和资源的真实路径，优先引用原有材料。

列出本次工具声明提供的各项功能及其实际入口，建立“功能 → 输入输出 → 环境 → 调用方式 → 原测试位置 → 包内测试入口”的对应关系。范围不明确时，与开发者确认需要纳入的功能；不能默默删掉失败功能来制造接入通过。声明功能均须有实际实现和最小测试。

核对工具已有的跨工具接口，按真实版本、调用方向和模式建立“参与工具/功能 → 接口入口 → 运行边界 → 依赖约束 → 联合用例”表。只列实际支持关系，不按工具名称构造任意组合；未提供接口、未测试或存在冲突的模式分别说明。

接入不改写或重排原仓库的源码目录，不往其中添加 AIMatterLab 接入材料。保留未提交修改、已有配置和真实任务。仅要求设计或准备材料时，将实际安装和测试记为 `not_run`；原程序缺陷或缺失功能单独报告，不通过修改源码把接入工作扩大为软件开发。

## 构成交付包

选择小写连字符工具 `id`，在开发者指定的工作空间创建 `<id>-package`，包含 `tool.json`、原软件独立完整 Git 仓库、包根交付 `SKILL.md`、人类说明和 `<id>-tests`。已有包内干净仓库可复用；首次获取仓库时保留原有结构，不移动或覆盖开发者正在使用的工作树。对未提交工作、worktree 或不完整仓库，保留原现场，准备独立候选副本后再注册。

将补充说明、薄封装和补充测试写在包内原仓库之外。它们以包根为基准定位原文件；不要要求原作者把文档或测试搬到指定源码路径。

交付包包含实际需要的源码和测试资源，不能仅引用原开发者机器上的另一个目录。模型或大数据可以放在包外层并声明为 `resources`，不要求提交进作者的 Git。尚未取得的资源记 `blocked`；安装环境和任务输出由计算资源及工作目录管理，不随源码打包。

按随附 [schema](references/tool-package.schema.json) 创建 `tool.json`，声明仓库路径与真实 `HEAD`、手册、前置指导文件、环境、逐功能 IO/参数/操作入口及测试映射。原作者只需维护原有源码和原位置测试；测试入口用相对路径重定向。运行 `node <本skill目录>/scripts/check-manifest.mjs <包根>/tool.json` 检查 schema、默认值与声明交叉约束；这一步不读取实际仓库闭包，也不安装或执行软件。实际注册还需 AIMatterLab 的包检查，约束见注册指南。

## 定义输入输出及参数优先级

按功能明确必需输入、可选输入、必需输出和可选输出，说明适用的类型、格式、单位、约束及依赖关系。每个可选项须有可执行的默认值或明确默认行为；可选输出也须说明默认是否生成及保存位置。

说明输入资源如何导入或引用、输出如何定位和保存，以及工作目录、命名和覆盖规则。交付 skill 和人类操作说明均须包含一致的输入输出契约；可以链接原仓库已有说明，并在包外层补齐缺项。

根据参数重要性、更改和调整频率确定展示优先级，标出优先向用户展示的参数，以及放入二级菜单的参数，并简述划分依据。核对已有软件默认值的实际来源；无法合理给定默认值的必需科学选择应明确列为必填。

## 声明环境并提供程序获取方式

声明各功能所需的平台、软件和依赖版本、CPU/GPU 要求、并行能力及最小运行配置。区分必需条件、可选能力和已验证范围；仅在相关时列出 CUDA、驱动、模型格式或工具链约束。

将实现全部声明功能的原仓库纳入包内，说明其来源、对应提交，以及实际获取、构建和安装方法。不能依赖开发者机器上的隐含路径或预装文件。需要构建时使用外部构建目录或隔离源码副本，避免将生成物写回包内原仓库。

开发者接入验证使用已有授权范围内的验证环境，记录声明功能和流程的实际覆盖范围。用户使用的计算资源、队列及真实安装配置由后续用户配置阶段确定。不要自动切换其他科学引擎的分支或改写已有环境登记；显式选择的后端不兼容时报告失败，不静默降级。

为联用模式分别交付构建、导出和运行依赖，声明版本范围、必要的精确锁定、模型格式、dtype、设备和 ABI 等实际限制。同进程依赖须在一个兼容运行环境内满足；独立环境不能解决同一解释器的版本冲突。顺序阶段可以分环境，但必须在实际消费环境重新加载落盘产物。使用现有 `guidance.configuration` 和测试映射交付这些材料；当前 v1 不接受自创联用字段，声明检查不会自动证明联合兼容。

## 生成交付 skill 和操作说明

生成可独立使用的包根 `SKILL.md`，按 [交付 skill 内容](references/deliverables.md#交付-skill-内容) 填写真实工具名、用途、软件提交、接口与文档定位、环境、安装、输入输出管理、测试和失败处理。不能用本接入指导原样充当交付 skill。

交付 skill 及其配套材料必须可迁移：使用相对于包根的资源定位、通用依赖与安装步骤，并将目标设备和输出目录写为调用时选择的配置。开发者的绝对路径、主机、队列、账户或凭据不固化到交付 skill；实际验证结论只保留其范围和证据说明。

人类操作说明可保留在原仓库的实际位置，并由交付 skill 定位；缺少内容时在包外层补充。说明应覆盖用途、安装、输入准备、参数设置、运行、输出读取和错误处理，并能找到包内最小测试入口。

交付 skill 可以调用真实 CLI/API；若软件提供 MCP，则按其实际实现说明启动、参数和返回。它须足以选择功能、准备输入、调用程序、定位输出、判断完成或失败及执行测试。相对路径及调用所需工作目录必须明确，不能只写一组文档链接或编造尚未实现的接口。

不要把 `operation.command` 声明当成已实现的通用执行器。当前自动用户配置闭环只支持固定的串行 CPU `installation.check/worker` 工程 reference；其他软件仍可声明、检查和注册，安装/执行适配按实际支持范围另行实现验证。只有需要演示该 reference 时使用 [小示例](references/registration.md#可选cpu工程示例)，不将它替换为开发者软件或科学验证。

接口应受其已有项目和资源授权约束；接入材料不授予额外文件访问或计算权限。需要接入 AIMatterLab 的实际接口时，检查当前实现再编写适配，保留其人工审阅和正式作业执行边界。

## 建立测试重定向入口

**接入测试的目的**：验证用户运行环境是否可用、声明的各项计算是否能实际运行——安装与依赖、设备/GPU、模型与输入加载、真实入口调用、产物生成和退出状态。它**不是代码正确性验证**；代码正确性、边界、数值精度和回归由原软件在发布其代码时验证。因此只保留满足该目的的最小用例，不要为追求“覆盖完整”把无关、重复或低级的仓库测试纳入接入包，以免占用交付空间和用户测试时间。

在包内提供 `工具名-tests` 总目录、整套测试介绍 Markdown 及各功能测试子目录。该目录是统一入口，可以将测试流程重定向到原仓库中作者实际放置的位置。详细结构见 [测试包要求](references/deliverables.md#测试包要求)。

每个功能子目录提供最简说明及必要的简短脚本或重定向入口，明确原测试、输入资源、工作目录、命令、预期输出和通过标准。优先薄调用已有测试；缺少检查时可在包外层补充测试或输出断言。不要复制维护同一套原测试，也不要仅打印固定成功文本。

测试代码、模型、数据、结构、配置和参考文件可以留在包内原仓库的任意已有位置，测试入口通过包内相对路径定位。需要补充的资源可以放在测试入口旁。完整性边界是整个 `工具名-package`，不要求资源集中在 `工具名-tests`；指向包外私有文件或只有下载地址的重定向不满足完整交付要求。

最小用例用于检查工具的输入输出契约、安装和环境配置，不用于验证代码正确性。按功能和声明的执行方式设置有界规模及资源，不以一个 CPU 用例证明 GPU 或并行方式可用，也不以短例证明科学精度、收敛或生产适用性。

为声明支持的联用模式提供最小联合用例，真实加载指定模型或偏置产物，经过实际接口执行并检查输出。on-the-fly 调用保留为同一运行任务，不能拆成每步另行提交的作业；力场—MD 与采样—MD 两项配对通过也不能证明三方组合可用。用例与证据要求见联用交付指南。

## 开发者接入验证

在已有授权范围内，按交付 skill 和测试入口完成安装及逐功能测试。检查整个包移动后重定向仍可解析，实际调用与包内仓库版本相符。若原测试会写回源码目录，优先配置外部输出或在隔离副本运行，记录实际使用的源码和测试身份。

对声明的计算流程核对从最初输入到最终产物的实际调用和资源匹配；复用已有最小用例完成相应流程验证。只验证了单工具功能时，按该范围记录，不据此声称未检查的工具组合可用，也不自动运行无关的完整科学矩阵。

使用新建且受 Git 忽略规则保护的运行目录保存实际输入快照、日志、输出和测试记录。检查接入前后的原仓库状态，确认未因生成接入材料或测试而改动源码。运行输出及私有连接信息不混入公共交付材料。

逐项记录安装和功能测试的版本、实际环境、命令、退出记录、输出检查、判定和证据位置。使用 `passed / failed / blocked / not_run`：实际检查通过才记 `passed`；执行或输出检查失败记 `failed`；缺少必要条件记 `blocked`；没有执行记 `not_run`。所有非通过项说明原因及下一步，不能用历史证据冒充本次测试。

修复后只重跑受影响的安装或功能测试，保留首失败和修复后的记录。作业状态未知时核对原任务，不自动重提。接入多个功能不意味着需要运行未受影响的 AIMatterLab 全套软件或科学测试。

## 保持仓库版本和重定向一致

在交付 skill 中记录包内原仓库对应的提交，以及安装、接口、说明和测试路径映射。在开发者授权下同步包内仓库版本后，核对这些映射；路径、接口、依赖或通过标准变化时更新包外层材料。

源码和原有测试随原仓库同步，生成的交付 skill、重定向入口和测试结果须绑定本次实际版本。仓库同步成功不等于安装或测试通过。已有任务引用的包和环境保持原版本，在候选包或隔离副本中验证升级，不原地改变它们依赖的代码或程序。

`git pull` 更新候选仓库后，记录新的真实提交，核对并更新包外层 `tool.json`、路径映射、交付指导和 wrapper；再检查、测试和显式注册更新。AIMatterLab 不自动 pull。包版本由源码提交、原始 manifest 字节和资源闭包共同计算，不能手填一个版本号覆盖旧快照。仅改变 wrapper 或说明也可能生成新包版本；详见注册指南。

## 向用户配置阶段交付

交付 skill 说明如何在用户选择的真实计算资源上安装、配置并完成对应测试。用户配置成功后，由该阶段的 Agent 根据实际环境生成执行 skill，收录正常操作所需的实际入口、环境、软件版本、输入输出、参数、命令和失败处理。

联用配置按用户所选模式的完整依赖闭包建立版本化运行单元；不要求所有工具共用一个全局环境，也不默认每个工具独立环境即可。执行 skill 应绑定实际参与版本、模式、运行单元及联合测试证据。当前通用科学工具组的自动解析、环境配置和组级激活尚待实现，不能因交付材料齐备而报告配置成功。

执行 skill 是该环境的日常工具入口。它生成后，之前的交付 skill、安装 skill 和配置指导由用户配置流程封存，保留版本与记录，不再自动读取。只有发生 bug 需要修复，或软件更新需要重新安装时，才重新使用所需封存指导并更新执行 skill。交付 skill 不应要求日常任务重新读取本接入指导或整套安装材料。

封存和激活是后端/worker 的权威事实，不由交付文件或 Agent 的成功文字触发。日常使用自足执行快照；显式 configure/repair/update 的人工授权只按准确版本、资源 ID、当前 owner/lease/revision 和有效期开放所需前置资源。失效激活保持封存，不能降回旧安装指导；未配置工具保留原指导路线。交付 skill 不创建授权、不改变项目权限，也不把 probe 当成配置成功。

## 交付和接入判定

交付 `<id>-package`：保留原仓库布局、提供 `tool.json` v1、独立交付 skill、人类说明和测试重定向目录，并补齐五项工具定义。整个包移动后重跑声明检查与实际文件检查；原有文档、接口和测试通过明确路径复用，额外接入材料位于包内原仓库之外。

同时交付逐功能对照和安装、测试结果，指出剩余缺项。只有五项定义满足，实际安装、所声明功能及流程的测试均通过，才能按本次明确的功能、流程、版本和环境范围报告接入通过。材料完成而环境或测试未通过时，报告材料完成及具体缺口。

若任务还包含 AIMatterLab 内部注册或适配，另外报告其实际实现和验证状态；工具包检查不替代运行适配器、前端或共享接口变更的验证。
