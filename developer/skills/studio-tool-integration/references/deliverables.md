# 工具接入交付指南

本指南将五项工具定义落实到开发者交付材料中。Agent 生成 `<id>-package` 和可迁移交付 skill，通过重定向复用原软件布局。机器声明采用 `tool.json` v1，完整字段、默认值和实际文件/版本约束见 [注册与版本契约](registration.md) 及随附 schema；目录树只作示例。

## 工具包的组织

```text
tool-name-package/
├── tool.json                     v1 机器声明，id 为 tool-name
├── SKILL.md                      生成的交付 skill
├── manual.md                     或引用原仓库中的真实人类手册
├── tool-name/                    原软件的 Git 仓库，内部布局保持原样
├── references/                   需要时补充说明和文件映射
└── tool-name-tests/
    ├── README.md                 整套测试的介绍与 Agent 执行入口
    ├── function-a/
    │   ├── README.md             最简测试说明及原测试位置
    │   └── run_test.py           调用原仓库测试的薄脚本或重定向入口
    └── function-b/
        ├── README.md
        └── run_test.sh
```

将 `tool-name` 和功能目录名换为实际名称。原仓库的文档、测试、数据和代码按作者现有位置保留，不必符合示意中的任何源码布局。介绍文档须为 Markdown，但不强制名为 `README.md`。缺少的接入说明、薄封装或测试放在包内原仓库之外。

完整性边界是整个交付包。测试资源可以位于包内原仓库，或包外层声明的文件/资源目录中，测试总目录提供可解析入口，不要求重复复制资源或把大型数据纳入 Git。`tool.json.tests.cases[].resources` 必须显式枚举所需文件或目录；资源目录递归纳入闭包。原仓库全部已跟踪文件和测试总目录也会完整纳入快照。包外层的其他被引用材料须在声明闭包内，否则注册快照不会自动包含它们。运行环境及任务生成物由计算资源与工作目录管理。

## 交付 skill 内容

包根 `SKILL.md` 是本接入指导生成的工具交付 skill，供后续用户配置阶段使用。它应有真实的 `name` 和 `description` YAML 元数据；名称采用适当的短工具标识和小写字母、数字、连字符，不直接使用中文占位名称。

| 内容 | 交付 skill 需要提供的信息 |
| --- | --- |
| 功能与流程 | 实际支持的功能、输入到最终产物的流程，以及开发者验证范围 |
| 源码身份 | 包内仓库位置、来源与对应 Git 提交，及必要的关联版本 |
| 文件定位 | 人类手册、输入输出说明、接口、环境要求和原测试的真实包内相对路径 |
| 安装与环境 | 通用获取、构建、安装方法，CPU/GPU、依赖和并行声明；目标环境由用户配置时确定 |
| 操作方法 | 实际 CLI/API/MCP 调用、输入输出和参数优先级、工作目录和输出位置、完成及失败判定 |
| 测试方法 | 测试总入口、各项测试的重定向、预期输出、通过标准及结果记录方式 |
| 用户配置交接 | 真实安装与对应测试通过后生成执行 skill，前置交付和安装指导按生命周期封存 |

明确“包根”为该交付 `SKILL.md` 所在目录。原始接口、说明和测试可以分散在原仓库各处，由交付 skill 和测试入口定位；说明不完整时在包外层补齐。交付 skill 应能指导实际操作，不能只有文件路径而没有调用方法。

希望选中交付 skill 时一并提供给 Agent 的说明，使用相对 Markdown 链接，例如 `[操作手册](manual.md)`、`[测试入口](tool-name-tests/README.md)`；测试介绍再链接子项说明。Studio 的托管读取器在版本闭包及权限允许范围内有界展开 `.md`/`.json` 链接，按每个引用独立检查封存与授权。裸文件名不自动展开，程序/大型文件保留为路径引用。合法链接重定向后的文档，其相对引用按原内容文件所在目录解析；不要依赖开发者机器的 cwd。

可采用如下重定向表；实际路径和命令从原仓库读取，不凭示例猜测：

| 功能或材料 | 包内原位置 | 统一入口或说明 | 调用目录与输出配置 |
| --- | --- | --- | --- |
| 某项功能的测试 | `tool-name/作者实际测试路径` | `tool-name-tests/对应功能/` | 填写该测试所需目录及外部输出方式 |
| 操作手册 | `tool-name/作者实际手册路径` | 由交付 skill 定位 | 普通文档读取 |

所有接入阶段生成的交付 skill 和配套材料应可迁移。环境要求和命令使用可配置的目标设备、环境和工作目录，不携带开发者机器的绝对路径、私有主机、账户或凭据。缺少现场信息时说明需要用户配置的项目，不预填用户环境已就绪。

## 五项定义的内容清单

### 输入输出资源说明和管理

按功能填写或定位输入输出说明，并使人类手册和交付 skill 或实际 Agent 接口中都可以找到一致内容：

| 内容 | 需要明确的事项 |
| --- | --- |
| 功能及入口 | 功能名称、真实调用入口、完成什么操作 |
| 必需输入 | 资源或参数、类型或格式、单位和约束；缺失时如何报告 |
| 可选输入 | 相同说明，以及省略后的具体默认值或默认行为 |
| 必需输出 | 应产生的资源、格式、含义、定位方式和完成条件 |
| 可选输出 | 开关或选择方式、默认是否生成，以及默认保存行为 |
| 资源管理 | 导入或引用方式、工作目录、命名、覆盖及保留约定 |
| 参数展示 | 重要性和调整频率、展示优先级、主界面或二级菜单归属 |

默认值应区分源程序已有默认与接入封装选择的默认，并给出来源或理由。用“无”“不生成”作为默认时应明确其含义。不要把示例中的某个科学参数当成所有任务的通用默认值。

输出说明应足以判断其能否作为后续工具的输入。若支持工具组，还应给出规范的流程定义，说明从最初输入经各工具的输入输出匹配到最终产物的关系；不能只列工具名称而不说明资源如何连接。

### 执行环境声明

| 内容 | 需要明确的事项 |
| --- | --- |
| 软件身份 | 软件版本、源码提交或发行件身份，以及有关安装依赖版本 |
| 平台与运行时 | 支持的平台、解释器或编译运行时及必要依赖 |
| CPU GPU | 各功能必需或可选的硬件、最小测试使用的设备配置 |
| 并行能力 | 支持的线程、进程或多设备方式，以及默认并行设置 |
| 特定兼容条件 | 相关时声明驱动、CUDA、模型格式、ABI 或工具链限制 |
| 可验证范围 | 哪些功能和执行方式有实际测试证据，哪些尚未验证 |

填写实际可用配置，不猜测未测试的硬件兼容性或性能。私有的集群地址、账户、队列授权和凭据由使用者在其运行环境配置，不作为公共测试数据。

### 最小测试用例

接入测试用于验证**用户运行环境是否可用、声明的各项计算是否能实际运行**（安装与依赖、设备/GPU、模型与输入加载、真实入口调用、产物生成和退出状态），**不用于验证代码正确性**。代码正确性、边界、数值精度和回归由原软件在发布其代码时验证。因此只保留满足该目的的最小用例，不要为追求覆盖完整而纳入无关、重复或低级的仓库测试，以免占用交付空间和用户测试时间。

遵守下方的测试包要求，覆盖全部声明功能，并能检查实际输入输出及环境配置。

### 人类手册和 Agent 接口

人类手册应覆盖用途、获取安装、输入准备、参数、运行、输出和错误处理，并链接测试总介绍。

生成的交付 skill 应明确适用任务、所需上下文、实际调用入口及参数、输入输出管理、测试方式和失败处理。MCP 若作为接口交付，应包含其实际服务实现或获取启动方式，以及实际参数和返回契约；仅有接口说明而没有实现，不满足可操作要求。可复用 CLI/API 加交付 skill，不强制为已有软件另建 MCP 服务。

### 程序代码及其获取方式

包内包含原软件仓库并保留 Git 管理方式，交付 skill 说明其来源、对应版本、必要依赖、构建或安装命令和实际入口。已有安装说明可直接引用，缺项在包外层补充。完整交付包还须包含测试所需的模型和数据等资源。

## 测试包要求

接入测试只覆盖用户环境可用性与声明计算的可运行性；完整回归、边界、数值精度和科学收敛测试属于原仓库发布流程，不纳入接入包。

### 测试重定向

统一入口可以使用包内相对路径映射、简短转发脚本或可迁移的目录链接，调用原作者实际放置的测试。原测试无需搬家或复制；同一测试只维护其原实现。重定向应明确目标脚本、资源位置、调用参数、执行目录和输出目录，转发真实退出状态并检查承诺的输出。

优先使用相对路径 wrapper。符号链接只允许可迁移的包内相对目标，目标闭包随包取得；绝对链接、越界、循环或 `.git` 管理目录引用会拒绝。Windows 上创建链接还可能需要系统能力，不把链接设为交付必需条件。manifest 路径写实际规范相对路径，链接自身的相对 target 才可用包内 `..`；两类规则不要混用。

所有文件定位以整个包为基准，从入口文件的位置解析，不能依赖调用者碰巧处于某个当前目录。重定向目标可以在 `工具名-tests` 外，但须在 `工具名-package` 内且随包存在。若原脚本会修改源码目录，使用其外部输出选项或在隔离副本中运行，并保留实际版本身份。

### 总介绍 Markdown

测试总介绍指导 Agent 执行整套任务，应包括：

- 工具身份，以及“功能 → 测试子目录”的覆盖表。
- 所需的已安装程序、执行环境和最小设备或并行配置。
- 逐项测试的入口；测试存在依赖时说明执行顺序。
- 各功能原测试和资源的包内位置、重定向关系，以及工作目录和输出目录如何配置。
- 每项测试预期输出和通过标准的定位方式。
- 结果记录位置与格式，以及未通过时的处理方式。

总入口可以是介绍文档中的命令列表，不要求额外编写一键运行器。

### 每个功能测试目录

每个入口目录的说明须让另一个 Agent 仅依靠完整交付包和已安装的工具环境执行该测试。可以引用原测试说明中已有的内容，写清：

1. **功能**：调用的实际功能和入口，检查哪些输入输出及环境要求。
2. **输入**：列出所有资源在完整交付包内的位置，附所需参数和默认值。
3. **最简配置**：设备、并行设置、数据规模、步数等，以及适用的运行时限。
4. **执行**：给出可以照做的命令或简短脚本，明确执行目录和输出位置。
5. **预期输出**：实际应生成的文件、结构、字段、形状、数值或其他可检查结果。
6. **通过标准**：将判定写为可核对的条件；数值结果需要容差时写清容差及其依据。
7. **结果记录**：说明应保留的退出记录、输出检查、结论和未通过原因。

根据功能选择有意义的判据。例如格式转换检查输出可解析且关键内容符合约定；模型导出检查保存后的产物可由声明的消费环境加载。进程退出码为零通常是必要条件，仍须核对承诺的输出。最小测试不承担生产精度或收敛验收，也不承担代码正确性回归；只选择能证明该功能在用户环境可运行的最小用例，避免无关、重复或低级的测试。

原测试或包外层补充的测试应运行真实工具，读取真实输出并在不满足通过标准时报告失败。测试输入、模型、数据、参考输出和辅助代码均须在完整交付包内，可以留在原仓库的各自位置。不能以包外机器路径或未随包取得的文件代替交付资源。

将整个交付包复制到不同路径后，交付 skill、重定向及资源引用仍应有效。运行生成物写入明确的新隔离目录，原仓库保持接入前的文件布局和内容。不要覆盖随包测试资源或将真实生产任务当作最小用例。

开发者接入验证还应核对声明流程中的输入输出匹配和最终产物，只报告实际测试覆盖的流程。用户环境的真实安装和对应测试在用户配置阶段另行完成。

### 测试所需资源不齐全时

仍应完成独立可完成的定义、说明和重定向，将具体缺少资源的功能标为 `blocked`。说明需要补入交付包的文件及其获取条件；不能把下载地址当成已包含的资源，也不能据此报告整个工具接入通过。

## 安装与测试结果记录

将实际安装步骤及逐功能结果写入运行报告。下面是报告内容清单，不要求某种特定机器 schema：

- 工具功能范围、软件和测试包的版本或源码身份。
- 交付 skill 与重定向对应的原仓库提交，以及实际流程验证范围。
- 实际测试时间、执行环境及 CPU/GPU 和并行配置。
- 安装方法、实际安装结果及证据。
- 各功能的执行命令、退出记录、预期输出与实际检查结果。
- 每项判定、非通过原因和证据位置。
- 尚未测试或不满足要求的功能和执行方式，及其下一步。

逐功能表可以采用：

| 功能或安装项 | 实际环境与执行方式 | 预期输出及检查结果 | 状态 | 未通过原因或未执行原因 | 证据 |
| --- | --- | --- | --- | --- | --- |

执行时填写真实结果，不预填成功。`passed` 表示实际检查通过；`failed` 表示执行或输出检查失败；`blocked` 表示必要条件缺失；`not_run` 表示未执行。重试保留之前的失败记录，不用最终成功覆盖它们。

日志和输出等原始证据保存在受 Git 忽略的运行目录，公共交付只保留不含私有信息的范围、结论和缺项。实际安装、全部声明功能及流程的测试通过后，报告对应版本、环境、功能与流程范围内的接入通过；不得由此推断任意环境、任意参数组合或科学结论已经得到验证。

另行记录 schema 检查、Studio 文件闭包检查/注册、开发者安装测试和用户配置结果。`definition_checked` 的安装与测试仍为 `not_run`；它不是接入通过。文档或测试 wrapper 打印 `passed` 也不能作为 worker 配置激活的权威证据。

## 用户配置阶段的交接

开发者交付的是可迁移的交付 skill。用户在 Agent 协助下，用已经验证可接入的工具，在其真实计算资源上安装、配置环境并跑完对应测试；这一阶段成功后才生成真实环境的执行 skill。

执行 skill 应包含日常操作需要的实际软件和环境身份、可执行入口、输入输出、参数、工作目录、调用方法及失败处理，并引用实际测试记录。现场路径与连接仅保存在用户私有配置，凭据只使用受控引用。开发者不能用自己的验证环境替用户预造执行 skill。

执行 skill 生成后，交付、安装和配置指导封存，不在日常任务中重复读取。只有发生 bug 需要修复，或软件更新需要重新安装时，才重新读取相应封存指导、完成真实检查和测试并更新执行 skill。原交付 skill 在包中继续保留，封存不等于删除作者的交付文件。

执行 skill 必须在其激活软件/环境范围内自足，不能要求日常重新读取交付 body、refs 或完整安装材料。后端受控指导读取和 worker 的路径读取门按实际包版本/环境/激活事实执行；repair/update 需明确人工授权，限定当前 owner、lease、revision、资源和期限。交付包不授予该权限。失效配置不会自动回退旧指导；其他尚未配置的工具不受此包的路由替代。这不声称隔离任意 shell 命令的文件读取。

目前真实自动配置仅覆盖固定串行 CPU worker 工程 reference；一般工具的注册、开发者接入测试和用户手动安装结果，不自动获得该配置能力。GPU、集群、MPI、科学引擎和一般安装器须分别实现并验证。
