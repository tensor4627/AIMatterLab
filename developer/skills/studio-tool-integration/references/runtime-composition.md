# 联用接口与运行环境交付

本指南适用于工具之间已有的真实接口，预置关注力场—MD 引擎、增强采样—MD 引擎两类。具体组合由实际接口决定，不承诺所有工具的任意组合。无跨工具接口时明确写明；有接口而缺少资源或验证时，保留接口事实并记录缺项。

## 开发者与 AIMatterLab 的职责

| 阶段 | 负责事项 |
| --- | --- |
| 工具开发者交付 | 核对支持的接口、版本及加载模式，提供可迁移使用 skill、依赖约束、最小联合用例和完整测试资源；报告自己的实际验证范围 |
| AIMatterLab 用户配置 | 读取并验证所选接口，计算完整依赖闭包，配置兼容的版本化环境，运行单工具及对应联合用例，依据真实结果生成执行 skill |
| 日常运行 | 使用已验证运行单元及其版本、模式和环境；在实际任务中经过原接口调用，保留 worker 的真实状态 |

开发者不替用户预造环境登记或配置成功。AIMatterLab 不能只分别安装各工具就报告联用就绪；也不要求开发者预构建所有用户平台的环境。材料中的指导不创建项目授权，不替代后端激活事实。

## 按运行边界交付接口

从源码、公开 API 和现有测试提取接口信息，不凭工具名或文件扩展名猜测兼容性。

| 运行边界 | 必须交付和验证的内容 |
| --- | --- |
| 顺序产物交接 | 生产者与消费者、格式和导出模式、保存/加载入口；允许不同环境，但消费端必须重新加载实际落盘产物并执行最小计算 |
| 同进程调用 | MD 入口及实际力场/采样 hook、导入与动态库依赖、调用约定；全部运行依赖须在一个兼容环境中满足 |
| 运行时跨进程通信 | 双方启动与停止、通信协议、数据/单位、同步次序及失败传播；可以分别登记环境，但必须实际联合运行 |

训练、导出和 MD 推理可以分阶段。不要把训练所需依赖无条件当作推理依赖；反之，加载完整 Python 对象、定制算子或运行时编译所需的模块也不能漏掉。根据实际加载路径确定闭包。

对每个支持的接口/模式提供一行记录，必要时附详细操作段落：

| 项目 | 需要填写的事实 |
| --- | --- |
| 身份与方向 | 本工具功能、对端工具/功能、实际已知源码版本或发行件身份；哪些是支持约束、哪些只是已测版本 |
| 接口与模式 | 源码位置、API/CLI、加载入口和运行边界；区分 eager、TorchScript、AOTI 等实际模式 |
| 依赖 | 平台、Python/运行库、精确 pin 或兼容范围、编译器、CUDA/驱动、C++ ABI/定制算子等相关限制及依据 |
| 数据约定 | 模型与输入的类型、格式、shape、单位、元素/原子编号、邻居表和截断、dtype、device；仅填写该接口相关项 |
| 调用与状态 | 初始化、每步调用顺序、力/能量/virial 与偏置的合成、历史更新、张量生命周期、同步/stream、重启和失败处理；说明实际支持的积分器等限制 |
| 操作指导 | 获取/安装依赖、准备输入、运行命令或真实 API 调用、工作目录和输出定位；目标设备与环境在用户配置时绑定 |
| 联合用例 | 对应的现有 `tests.cases` ID、测试说明、资源来源、设备、规模、时限、产物检查及通过标准 |
| 验证范围 | 参与版本、模式和实际设备；逐项 `passed / failed / blocked / not_run`、原因与证据；没有执行时不预填通过 |

同一扩展名不代表同一接口。例如两种 `.pt` 导出可能采用不同元素编号、dtype 或目标引擎约定；必须依据导出/消费代码填写。未明确支持的模式不得静默更换模型、后端或放宽版本 pin。显式选择的 AOTI 不兼容时必须失败，不能改走其他后端。

## 使用现有 v1 交付，不自创机器字段

当前 `tool.json` 和内部 `manifest.json` 仍为严格 v1；尚无机器可解析的联用接口或运行单元字段。本指南规定交付内容，**不宣称已实现自动依赖求解、组级配置或执行**。未来结构化契约须采用显式版本化扩展，并保留现有包、登记环境及真实任务。

工具本身的实际环境要求继续写入现有 `environment.requirements`；按模式区分的详细约束和来源写在联用说明中。不能只在指导中隐藏必须满足的工具依赖，也不能把已测版本误写成唯一支持版本。

对内部工具：

1. 在 `aimlab-tools/` 下、`tests/` 外创建联用说明，例如 `aimlab-tools/runtime-composition.md`，填写上述接口表和操作方法。
2. 将该文件加入既有 `manifest.guidance.configuration` 数组，并从 `aimlab-tools/SKILL.md` 用相对 Markdown 链接指向它；手册与测试总介绍也应能定位接口及联合用例。
3. 用已有 `tests.cases` 声明联合用例。每例仍有一个真实 `function_id`；参与另一工具时，在用例说明中列出对端身份、模式、依赖和外部资源获取条件，不增加 `members`、`couplings` 等未知字段。
4. 与该功能的 `functions[].tests` 保持双向映射。补充 wrapper 和资源只写入 `aimlab-tools/`，不修改其他源码或切换兄弟引擎分支。

以下仅是现有 manifest 中 `guidance` 字段的片段，不是完整声明：

```json
{
  "guidance": {
    "configuration": ["aimlab-tools/runtime-composition.md"]
  }
}
```

第三方 `<id>-package` 使用包外层原仓库之外的联用说明文件，在 `tool.json.guidance.configuration` 声明包相对路径，并由交付 skill 链接；按已有用例格式和资源闭包规则交付联合测试。

对端程序按其自身的版本化工具来源取得，不将开发者机器上的另一个目录当成交付资源；测试所需模型、输入、配置、参考文件和 wrapper 必须随声明闭包可取得。缺少任一必要资源时明确记录 `blocked`。

声明检查仅覆盖现有 schema、路径闭包及功能/测试映射；**不会解析本表、确认对端接口或证明版本兼容**。这些事实须由 AIMatterLab 配置流程核对并实际验证；在相应适配能力尚未实现时明确报告未实现，不能用成功文字替代配置。

## 完整工具组的最小联合验收

AIMatterLab 应按用户选择的实际模式解析全部参与者及传递依赖，划分运行单元并建立兼容环境。同进程版本约束冲突时不能用两个 venv 规避；报告冲突与受影响模式，不改写原登记或自动换后端。不同运行单元可以使用不同环境，不要求所有已接入工具共用一个全局环境。

联合用例须证明接口在目标环境可运行，保持有界规模：

- 记录源码/包身份、环境身份、模式、实际设备和序列化产物哈希；重新加载该产物，经过真实接口检查声明的输出形状、单位、有限值及有关约束。
- 力场—MD 用例必须由 MD 实际调用力场，执行少量明确步数；增强采样—MD 用例必须经过真实采样 hook，并检查对应偏置输出/状态。所需模型和偏置都必须是真实测试资源。
- 若支持共享 GPU 内存、DLPack 或异步 stream，覆盖实际使用的数据与同步边界；若接口更新历史，检查其约定的提交时机，不能只检查 import 或进程退出零。
- on-the-fly 调用在同一运行任务内发生，不拆成每个 MD 步独立提交。力场—MD、采样—MD 两项配对通过，不能推出“力场 + MD + 采样”完整组合通过。开发者为自己声明支持的组合交付接口侧入口和资源；AIMatterLab 对用户实际选择的完整组合复用或编排相应最小用例，保留独立联合证据，不能要求单个开发者预验证任意对端组合。
- 逐项保留退出记录、真实输出检查、非通过原因及 `passed / failed / blocked / not_run`。缺条件和未实现部分与执行失败区分；原始证据写入隔离且受 Git 忽略的运行目录，公共交付不含私有连接信息。

上述检查用于证明声明计算在该环境可运行，不代替算法正确性、长时间 MD 稳定性、科学精度或收敛验收。只运行所选模式相关用例，不默认扩大到全工具、全模型、全硬件矩阵。
