# AIMatterLab 五方面设计审查

2026-11-18，0.1.8 之后的待发布源码，最终核验基于本地提交 `12a26dd` 及本次工作区改动。此次沿用户路径检查了打开历史会话、选择计算服务、形成输入快照、查看作业、撤销和输出复现包。判断依据为[软件规范](../software-specification.md)与[架构说明](../architecture.md)。

## 设计判断

| 方面 | 值得保留的设计 | 实际薄弱环节与本次处理 |
| --- | --- | --- |
| 前端设计 | 工作区与 Agent 同屏，用户核对输入或作业时可以保留草稿。导航、输入焦点和终端高度支持键盘操作。 | 笔记本窗口里，统计卡、来源信息与五项筛选排在作业之前。已压缩统计卡，常用筛选直接显示，时间与项目可展开。来源异常自动展开，无匹配时只显示一个清除入口。 |
| 后端实现 | 桌面保存索引，worker 保存运行事实。目标关联输入、不可变快照与产物回执，使复现有可核查的依据。 | 复现包生成时，合并清单覆盖了原先准备写入的运行对象。现保留旧版运行 ID 字段，另写执行命令、环境标识、参数与快照清单。缺失副本列出原始哈希和缺失原因，内容被修改时拒绝导出。 |
| Agent 服务 | 不同服务商使用各自适配器，计算作业由 worker 管理，历史可按会话和轮次回放。 | DSH 的请求超时曾提前释放会话，晚到的文本或错误可能归到下一轮。现按原请求和原会话跟踪回执，待核对期间限制同一会话的下一轮。同一运行时的其他会话可继续。DSH 与 API 桥共用中断历史恢复逻辑。 |
| 计算服务连接 | SSH 登录、终端操作权、作业服务健康状态、工作流权限分别记录，符合复用已登录连接的工作方式。 | 旧 WSL 连接失败的清理可能关闭刚接好的 SSH 服务，等待中的 WSL 选择也可能重新占用连接。现将选择顺序与传输的生命周期分别核对，只允许当前连接清理自身，重复选择同一目标共用待办请求。 |
| 作业管理 | 本地与集群作业分别保有记录，提交结果未知时可以核对原作业。 | 修正了跨服务同号记录互换、按裸 ID 覆盖不同类型作业、用上一次调度查询的身份撤销作业，以及把通用 LSF `EXIT` 归为已撤销。现在分别核对服务、记录类型、作业 ID 和本次身份回执。 |

## 三个容易误判的操作

**切换资源后回到作业。** 在服务 A 打开记录，再切到也保存了同号作业的 B，桌面会返回记录列表。A 的迟到响应不能覆盖 B 的列表。首页、底部队列、命令搜索、训练页和运行列表复用同一打开逻辑。行上的“返回会话”会核对任务、服务、记录类型、会话与提供商。在有已核验服务身份的列表里，老任务缺少可比对的绑定时不提供这条快捷入口。只读查看与执行授权分别判断。[桌面入口](../../frontend/app/App.tsx) · [来源核对](../../backend/main/compute/worker-service-version.mjs) · [任务关联](../../backend/main/workspace/routes.mjs)

**Agent 超时后继续聊天。** 同一会话须等原回执，或明确断开并重新连接。迟到的原回复不会作为新轮内容接收。历史记录区分本地接收超时与原服务后来确认的结果，供应商错误从对应轮次读取。中断时没有回执的工具会显示结果未确认，用户可核对原操作。[DSH 适配器](../../agent/providers/dsh.mjs) · [API 模型桥](../../agent/providers/api-model-bridge.mjs)

**点击撤销直到看到终态。** worker 先持久化撤销意图，再核对原作业。并发点击共用一次在途撤销。命令回执丢失时，送达情况保留为未知。通用失败、调度器确认的撤销、成功退出回执分别处理。本地旧运行缺少可验证进程身份时也保留撤销意图。[本地运行](../../backend/worker/studio_worker/compute/runs.py) · [集群状态与撤销](../../backend/worker/studio_worker/compute/cluster.py) · [集群详情](../../frontend/features/cluster/ClusterPage.tsx)

## 仍值得投入的改进

1. **整图执行的覆盖范围。** 本地 WSL 已有 `gpumd.md → trajectory.density` 路径。单个集群作业已有提交与监控，整张图的 SSH/Slurm 冻结、节点恢复和上下游消费回执仍待接入。若希望同一工作流从本地迁到集群，可以用同一小图检验能否找回中断前的调度编号、能否证明下游读到同一份产物，以及每个目标能否给出验收结果。[执行入口](../../backend/main/workspace/roadmap-execution.mjs) · [流程图实现范围](../development/workflow-io-roadmap.md)
2. **工具组的真实环境核验。** 固定 CPU `installation.check` 是通用配置器的工程参考。增加工具组时应为对应引擎、模型格式、设备和实际产物消费补齐联合测试。这样可以向用户说明某个具体环境能执行哪条路线。[软件规范的计算资源章节](../software-specification.md#计算资源)
3. **工作台状态的维护成本。** 目前 `App.tsx` 同时处理记录来源、会话选择、导航和刷新。本次让各作业列表入口共用同一判断。后续可把来源核对与记录详情导航一起移入运行记录模块，以“打开期间切换资源”和“同号、不同服务”两条交互作为回归边界。视觉上可继续统一其他高密度页面的次要控件。本次直接调整的是运行记录页。[运行记录页](../../frontend/features/runs/JobsPage.tsx)
