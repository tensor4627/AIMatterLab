# 1.0.2-dev.9：SSH 接入提速与恢复诊断

2026-11-11。用户反馈点击“连接作业服务”长时间等待且失败，要求重新研究整套连接流程。本代改变 SSH 连接层，不修改科学引擎、注册环境、项目授权或真实作业。

用户随后明确要求“不要封装便携版，只改 bug 和测试”。已停止后续封装与便携交付；最终修复使用源码定向测试和现有 Electron 验证。此前产生的测试包及其失败/通过证据保留，不作为最终源码的交付包。

## 调研与行为

只读诊断确认原尝试停留在启动超时、通道仍被保留的状态。旧版没有分阶段信息，不能据此认定服务器缺少 Python、网络不通或作业服务已经启动成功；没有重试、输入、断开或重置用户的原 SSH。

- 继续使用用户已认证的同一条 SSH。小型单行启动器先报告 Python/SQLite 与终端条件，再核验连接层和 worker 缓存；缺失时才传输。完整 worker 清单改为有界 gzip，内容逐文件与整包核验，不安装 Python 或科学环境。
- 连接层 Python 文件放在 worker 之外，单独按完整 SHA256 缓存。dev.8 的 138 个 worker 物理文件与运行指纹保持不变，已有 worker 与 SSH 任务来源不因连接提速而改变。缓存损坏拒绝接入，保留明确诊断，不默默替换已运行服务。
- 界面显示正在等待 Python、核验缓存、传输、启动服务、核对身份/工具等实际阶段；传输数字来自收到的确认，不制造整体百分比或预计完成时间。首次 Python 响应有独立超时，明确区分“没有收到响应”与“不支持所需版本”。
- 用户可以明确停止接入。准确尝试 ID 在桌面桥和后台保留取消记录，阻止取消之后迟到的启动请求；只有退出协议与新的 shell 恢复证明通过，才交还终端。状态不明继续保留通道，不自动重连、重发或切换到另一个计算资源。
- Windows ConPTY 返回的是屏幕重绘序列。对完整且属于当前尝试的帧，只识别帧外有界的已知光标、擦除和可见性控制；完整内容内部保持严格 Base64/JSON 校验。停止帧的 shell 控制仍须准确匹配并通过新的恢复证明，不能用通用删除控制字符来猜测协议成功。
- 已确认返回终端后，清除本次接入遗留的等待阶段与错误；较旧接入的拒绝/成功回执都不能覆盖新尝试。启动请求已超时而尚无服务 ID 时，仍先登记准确取消记录，不能凭一次 idle 观察就宣布安全恢复。终端自动适配尺寸仅提交后端允许范围内的整数尺寸，临时过小布局不再制造无效请求。
- 核对真实身份、服务健康、工具能力后才启用任务编写。任务规划、项目授权、输入审阅及执行批准继续独立生效，登录节点本地科学运行仍被拒绝。桌面退出关闭自己的 SSH，已提交作业和远端 worker 保留。

缓存保存经过校验的软件文件。SSH 会话仍由用户在本次桌面新建，正常退出断开，下次启动由用户明确选择保存配置重新连接。

旧版每次完整传输 604 个 INSTALL 分片及 604 个确认；同一份 worker 清单使用 gzip 后为 181 个分片和 181 个确认，worker 传输线字节从 2340416 降到 701697（减少 70.02%，不包含小启动器和连接层首次传输）。这是字节核验结果，不等于连接耗时减少 70%。实际冷/暖耗时与环境另列，不给用户集群速度作保证。

没有将 SSH 转发设为必需条件。[OpenSSH 的本地转发](https://man.openbsd.org/ssh.1)可在允许转发时复用认证连接，但现场入口可能禁止转发，[公开集群文档](https://doc.nju.edu.cn/books/efe93/page/a1d0c)也明确存在此限制。[Windows OpenSSH 的支持范围](https://github.com/PowerShell/Win32-OpenSSH/wiki/Project-Scope)没有通用 ControlMaster 支持。因此当前采用同一 PTY 的兼容路径；独立转发只作为未来明确支持的配置选项，不自动启动另一条登录或改变集群策略。
