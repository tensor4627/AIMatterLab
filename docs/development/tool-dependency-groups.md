# 工具依赖组与环境配置覆盖审查

本次审查针对当前工具接入与配置能力。结论是部分覆盖：已有产物交接、组合检查及目标环境验证原则，也已有工具组 DAG 声明；尚未实现科学工具组的运行时依赖契约、联合环境求解和组级配置验收。本文是设计与审查记录，不是已实现的新 schema 或已通过的科学测试。

## 已明确的产品职责

预置联用类型覆盖所有已声明支持接口的力场与 MD 引擎，以及增强采样工具与 MD 引擎。这里预置的是接口类别和配置规则，具体支持关系来自开发者交付的真实接口；不建立任意工具/版本的笛卡尔积兼容承诺。

开发者在 `aimlab-tools` 中交付本工具提供或接受的版本化接口、支持的连接方式与加载模式、使用 skill、必要依赖/模型约束和最小联合测试。无需开发者为每个用户预建完整联用环境，也不要求双方重复维护同一套测试源文件；测试应通过已声明接口使用对端环境和可重定位的资源。

AIMatterLab 负责处理这些交付物，核验所选对端及实际接口，解析所选完整组的依赖闭包，按共同运行单元配置兼容环境，并在真实目标中完成对应测试。必须覆盖实际选择的所有联用成员，而非只安装各自的独立环境。一个 MD＋力场＋增强采样的共同运行单元必须统一求解并联合验收；两个对分别通过不能替代三方组合的证据。

AIMatterLab 的组配置结果应绑定完整成员、源版本、接口/加载模式、实际环境和产物身份，并据此生成执行 skill。skill 提供使用方法，不能扩展机器可核验的支持范围、改变项目授权或代替实际通过回执。现有 v1 包继续按原能力接入；缺少新联用声明时，组级能力保持未声明/未验证，而不是删除旧包或自动认定兼容。

当前科学能力面板的功能分类与版本化工具组是两个概念。把工具列在同一个界面分组下，不建立它们共同执行时的依赖关系。

## 分清执行顺序与运行时依赖

执行先后与依赖形式是两个维度，不能用一个 `depends_on` 替代。

| 依赖形式 | 环境安排 | 必须验证 |
| --- | --- | --- |
| 文件产物交接 | 生产者与消费者可以使用不同环境 | 实际产物哈希、格式、模型类别、元素/原子序号约定、单位、精度，以及在真实消费者环境中的加载与调用 |
| 同一进程内 import、回调或逐步受力计算 | 这些运行时成员必须在同一个解释器/运行环境中兼容 | 完整 import 和动态加载依赖闭包、Python/Torch/CuPy/CUDA、设备与张量互操作，以及实际联合调用 |
| 原生库或编译模型加载 | 生产环境可分开；消费者进程中的库与产物必须满足其加载约束 | LibTorch、CUDA、C++ ABI、GPU 能力、dtype、输入/输出 ABI 和实际加载运行 |
| 显式独立服务/进程通信 | 可以分环境，但必须已有真实协议实现 | 协议、数据/单位、状态、时序、生命周期和故障处理；不能为了回避依赖冲突而虚构远程接口 |

先后执行也可能有同进程依赖：例如上一步保存整个 Python 模型对象，下一个步骤的反序列化可能需要模型类及其库。反过来，导出为可独立加载的格式后，消费者未必需要安装训练工具的全部依赖。应从实际加载路径确定。

## 当前源码的具体组合

以下是源码审查结论，没有执行新的联合运行。

审查身份固定为 2026-11-09 的 PyDyn `parallel@1cdcbdc58922`、HotPP `aimlab@e5d0cc52b0c6`、pyGAS `aimlab@4d981f828385`、GPUMD `aimlab@2c716d714afb` 和 TorchNEP `aimlab@4c3474ba9319`；下列具体实现与版本限制只对应这些源码身份。源分支后续变化时应重新核对，而不是沿用本表声称兼容。

| 组合 | 源码实际路径 | 配置与验证要求 |
| --- | --- | --- |
| HotPP 导出 → 普通 PyDyn | `MiaoForceModel` 使用 `torch.jit.load(...).cuda()`；HotPP 分别导出 ASE 与 LAMMPS TorchScript，后者包含元素索引重映射 | 训练/导出环境可以独立；PyDyn 应消费匹配其真实原子序号接口的 ASE 导出，并在实际 Torch/CuPy/CUDA 环境验证。不能只比较 `.pt` 扩展名 |
| HotPP eager 模型 → 优化 PyDyn | `OptimizedMiaoForceModel` 可用 `torch.load(weights_only=False)` 加载 eager 模型，并直接导入 `hotpp.inference.PreparedInference` | PyDyn、HotPP 及其完整 Python 导入链必须在同一运行环境可用；还要验证同 CUDA 设备、几何精度、邻居表和属性支持。该受力调用属于 MD 的运行时组成部分，不是每一步独立提交一个 HotPP 任务 |
| PyDyn ＋ pyGAS | 当前 PyDyn 使用 vendored `pydyn.bias` 参与同进程受力和 simulation hook | 单独安装、测试上游 `pygas` 不证明 vendored 实现或其 ABI 相同。记录实际模块来源和版本，验证真实 bias 加载与联合调用 |
| pyGAS 产物 → GPUMD/GPU-Sampling | 模型由消费者进程内的 LibTorch/AOTI loader 加载 | 可以分生产和消费环境；必须在选定原生二进制和目标 GPU 中验证同一产物。当前源码的 AOTI 编译/原生消费路线有 Torch 2.13.0 约束，Python loader 还按所选 manifest 校验完整工具链身份 |
| TorchNEP → 原生 NEP 消费程序 | 模型文本还涉及部署目标、网络结构、物种顺序和原生实现支持 | 按实际目标导出并验证，不能把训练保存的 `.txt` 改名后当作所有原生程序都可用 |

精度也属于连接约束：当前 HotPP 声明测试导出使用 `--double`，普通 PyDyn 的默认模型输入采用 FP32。需要明确目标模式并用实际产物调用验证；这是源码指出的待验证风险，不能把它报告成已经观察到的运行失败，也不能在产物哈希校验后静默转换模型。

当前 HotPP 声明固定 Torch 2.11.0+cu128，而上述 AOTI 路线绑定另一套工具链。同一进程组合不能靠两个 venv 满足互斥约束。应给出冲突来源；仅在用户明确选择可兼容的版本、模式或后端后建立另一个版本化配置。显式选择的 AOTI 失败时不得改用 TorchScript 来报告通过。

## 接入与配置指导应补充的内容

1. 接入时记录函数实际使用的运行时组件、可选加载模式、动态导入和原生依赖，而非只列包名或安装命令。把阶段间产物交接与函数内部的实时调用分开。
2. 为每条产物连接记录生产者/消费者的固定版本、导出目标、格式、精度、物种/原子序号与单位，以及加载验证入口；有自定义类或算子时记录消费端依赖。
3. 配置前按必须共同运行的成员形成运行单元，求这些成员的兼容约束交集。每个运行单元配置一个版本化环境；分阶段交接可以使用不同环境。不能只采用“每个工具一个环境”，也不必强制所有工具共用一个环境。
4. 冲突时保留来源及失败/阻塞状态，不自动改依赖 pin、切换源分支、替换 artifact 或更换执行模式。
5. 开发者交付其支持接口的最小测试入口与资源，AIMatterLab 对用户实际选择的完整组合执行验收：生产者实际生成或提供固定产物，消费者按哈希读取，在真实目标环境完成加载、一次能量/力/必要 virial 调用；若该组合声明进入积分或采样，则再运行对应的有限步联合用例。验证实际形状、有限性、单位和生命周期，不要求增加长轨迹或精度回归，也不要求单个开发者预验证任意对端组合。
6. 分别记录单工具安装、单工具测试、连接兼容和联合运行结果。单工具测试通过不能升级为组级 ready；新配置变更后，失效的是受影响连接和运行单元的证据。
7. 生成执行 skill 时绑定已验证的组/运行单元、环境和源版本、实际程序/模型加载方式及支持的属性。未实现的组配置接口保持 unavailable，不以文字说明替代执行能力。

## 契约与实现的后续工作

现有 v1 schema 拒绝未知字段，不能直接给 manifest 塞入未支持的运行时关系字段。应在保持现有包、登记和真实作业兼容的前提下，设计版本化的组合契约，包含阶段依赖、产物边、运行时成员、每个运行单元的环境身份及联合验收绑定，再同步实现规划、探测、执行和恢复的相关约束。

这要求同时覆盖开发者接入指导和用户环境配置指导。只更新 skill 文字不会让当前固定 CPU 配置器获得科学组合执行能力。当前独立工具安装批次已暂停，14 项单工具测试仍是准备状态，没有任何工具安装或测试被计为本轮通过。
