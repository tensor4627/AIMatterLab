# GPU Sampling Studio development evidence loop

Use this runbook for an explicitly requested multi-round Studio development review. Keep it in development documentation; do not inject it into scientific Agent conversations. The workflow-authoring skill remains a separate product capability.

## Roles and one-round gate

| Role | Responsibility | Required current evidence |
| --- | --- | --- |
| A · user and scientific tester | Operate the actual Electron UI with ordinary language and clicks; run affected scientific routes only when execution/numerics changes need real verification | Natural user prompts/actions/replies and same-page/file checks; actual run IDs, exits and output assertions only for necessary scientific checks |
| B · engineer | Diagnose observed friction, implement assigned changes and turn portable learning into narrowly scoped skills | Reproduction, observation versus inferred root cause, changed behavior, source/component tests and raw evidence references |
| C · responsible reviewer | Independently challenge scope and verify whether each round deserves acceptance | An explicit passed/rejected verdict with source/evidence hashes, unresolved defects and retained rejection history |

The parent coordinates shared file ownership. A round needs a concrete user-visible improvement or a correctness/reliability repair; renaming a phase or repeating an unchanged test is not a new iteration. C must accept the current round before the next round's tracked changes begin. Rejected attempts remain in the evidence record and are repaired within the same round. Complete the number of rounds the user requested rather than silently shortening the loop.

Explicit user role/model assignments take precedence over this default table. Record who owns completeness testing, independent workflow-use counts, implementation and final review before dispatching work; source review or another actor's UI actions cannot substitute for an independently assigned native workflow tester.

## Evidence collection

Before each round, identify the modified layers, behaviors and dependencies and select checks for that scope. Record affected application source identity. Frontend-only work does not need backend or engine executions. Backend-only work gets affected API/state/persistence checks. Shared contracts need the relevant checks on both sides. Use fresh ignored run/worker roots when the chosen checks require them, and isolated profiles for native UI tests. A deliberate resume/recovery test may reuse a test-owned profile and inspect its relevant saved state without rerunning unrelated computations. Record affected sibling-engine identities when real engine checks are necessary. Preserve production profiles, SSH registrations, credentials, authorizations and real queued/running/unknown jobs. Never switch engine branches or automatically resubmit an unknown job.

An isolated test project still has an explicit authorization scope. A tester must not change its policy when the parent forbids policy edits. For an authorized edit, capture the exact project identity and full pre-change policy, inspect the UI change list, and verify the saved result before executing. If that baseline is unavailable, stop the policy edit and report the missing evidence. After an accidental edit, preserve the incident, restore only values supported by evidence under a specific correction instruction, and read back the result; do not claim a complete historical rollback from a partial baseline. This is a development-test rule, not an extra product approval step.

A maps scientific impact only when changes can affect execution or numerical behavior and contract tests cannot establish the result. Then run only the affected bounded routes, retaining actual inputs and outputs. An explicitly requested full scientific acceptance may cover PyDyn MD, GPUMD MD, PyDyn-pyGAS sampling, GPUMD GPU-Sampling, NEB and implemented training/evaluation/export/analysis routes; that matrix is not a default for every dev. For unaffected routes reuse identified evidence at its original version, or record not_run_this_change with the reason. Mark genuinely required checks blocked when fixtures or environments are missing. Keep backend route evidence separate from the actual native UI chain; neither substitutes for the other.

For UI evidence, use natural goals and supplied scientific inputs. Do not make the prompt an internal tool recipe, prebuilt graph JSON or list of private task/project IDs. Exercise initial authoring, human review, execution confirmation where authorized, and same-conversation continuation. Verify saved source/graph/config files and hashes, not just an answer or green dot. Include actual file selection, manual parameter editing, navigation and reopening when they are part of the change. Model behavior is not proven by direct IPC calls or a mock service. Before confirming deployment, wait for the actual current prepared run identity and revisions, completed asynchronous preparation and its real input snapshots; an already visible historical snapshot list is not a new preparation receipt. Preserve disabled gates and report races rather than forcing a click or reusing a check.

Independently audit actual exits and finite/structural output assertions. Separate input completeness, adapter validation, artifact reload, runtime integration, optimizer stopping, sampling coverage and physical validity. A short engineering example cannot prove model accuracy, production stability, a reliable barrier or a converged free-energy surface. A draft-only user request must stay draft-only; developer artifact checks use a separate copy and are labeled separately.

## Engineering and review records

B writes a private per-round review with reproduction, observed effect, probable cause, specific change, current validation and remaining limits. Keep discovered failures and recovered attempts. C checks the raw evidence and source diff independently; mock/component tests are useful software checks but are never current scientific runs. If source changes after an evidence snapshot, record the new identity and assess which checks need rerunning.

Use typed, main-process-validated IPC. Keep the renderer free of filesystem, process and credential access. Project authorization remains outside MCP control. Scientific parameters and actual executable inputs must agree; do not modify a comment, evidence note or hash marker to bypass stale-input protection.

Store private prompts, machine paths, connection details and raw reports only in ignored runtime roots. Public iteration notes describe behavior, coverage, passed/failed/blocked/not_run and limitations without SSH/proxy endpoints, accounts, credentials or private research inputs. Public skills contain portable reasoning and tool contracts, never developer-machine recipes. Update CHANGELOG and the version document. Verify the actual package before a local release tag; do not invent historical commits or push without authorization.

## Native audit scheduling and startup diagnostics

Separate application health, native control-channel health and functional acceptance. After a native failure, retain the first evidence, check the actual window and launch process, refresh the selection and retry once using the official recovery procedure. If capture fails but an exact target and focus remain observable, a bounded harmless native keyboard check may establish input separately. Do not spend repeated batches on the same failed channel or count a recovered window as a button pass.

A command executor can launch a GUI with inherited restrictions that differ from the normal desktop user. Preserve the exact executable, loaded package, isolated profile and launch context. For a native startup error, collect one bounded supported Chromium file log; Windows child stderr alone is insufficient. Diagnose the failed check before changing application code. Do not disable Electron sandboxing, erase profiles or caches, reset ACLs or alter system security based only on an exception number. A diagnostic's suggested cause is not independent evidence of directory permissions.

For a Windows application-error popup, inspect the System log's Application Popup events as well as Application Error/WER records, and correlate exact event times with the individual launch receipts. An empty Application log does not establish absence of a native popup. Keep an unexpected exit with code zero separate from a recorded exception popup. A diagnostic process or dump collector exiting does not prove its system error dialog was dismissed. Before closing the diagnostic, identify any remaining native dialog against its exact event/dump and verify it actually disappears; do not close unrelated healthy Studio windows. Do not repeat the same failed restricted-context launch; reuse one verified normal-desktop instance and keep the explicitly approved frontend controller attached across batches. Do not weaken Electron security to make a test launcher work.

Frontend automation must count exact targets before clicking, stop on missing or ambiguous targets, and use bounded waits. A locator error is a test-infrastructure failure, not evidence of a broken product button. Capture the first failure and correct the locator without silently replaying actions. An attach-only controller must not own application shutdown, call per-batch process exit or start replacement instances after an uncertain response.

Before any Windows Electron launch, including legacy native smoke scripts and unpacked binaries, run the common `node scripts/start.mjs --preflight-only` check in the intended execution context. A restricted-token result requires a normal desktop execution context, not an automatic permission escape, repeated launch or Electron sandbox flag. Standard source start/dev and one-prompt launchers already enforce this boundary. See [the confirmed native failure and scoped repair](../../../windows-startup-diagnostics.md). Normal limited user tokens are supported; this is not an administrator requirement.

Keep GUI host lifetime explicit. If the command host must remain alive, retain that specific host and verify the app through the official window inventory or read-only process identity; do not block on a GUI-waiting terminal poll. An absent workspace while a known portable launcher is still alive can mean extraction is ongoing. Observe the same live handle rather than launching a duplicate. A deliberate product update requires a current idle-state observation and exact old-process guards; it does not count as native Close-button acceptance.

Freeze one source/package identity per acceptance batch. Group controls by page and reuse owned fixtures, preserving the required state-before/action/state-after correspondence and all changed values. Separate functional activations, navigation, keys, optional QA and setup. Inspect aliases and dynamic states without silently dropping untested entrances. A single actor owns native UI input; read-only source review, package audit and independent scientific evidence work may proceed in parallel. Offline global queue observation does not block harmless navigation, and never becomes evidence that jobs are idle.

For keyboard-only native batches, prove focus before activation. An indexed value readback is not focus evidence; setting an already-equal value may leave focus elsewhere. A temporary view-only search marker followed by exact selected-text readback can establish a bounded anchor. Preserve the first immediate observation and allow a fresh settled observation without repeating the key. Never clear a document-wide selection or send a marker. Derive a finite Tab route from the actual current tree and source, including off-screen historical controls, group headers, disabled controls and scrollable previews. A tester may authorize that finite batch in advance; the input proxy performs one action followed by a fresh observation at each step and stops on any owner, order, layout, modality or busy-state change. Do not require a new parent decision for every key in an already-reviewed deterministic route. Keep these recovery keys separate from scientific-button importance. Restore all temporary view filters explicitly. After Prepare, do not edit deployment settings merely to regain focus. No repeated Prepare, Execute or Send after an uncertain acknowledgement.

Use verified unpacked development artifacts for ordinary iterations; compress a portable package when its distribution/startup boundary actually needs validation. Do not rebuild or rerun unchanged checks solely because an observation timed out. Regress only changed behavior and affected dependencies: version increments, text/layout changes and UI audits never trigger a full software or scientific matrix. Full matrices need an explicit comprehensive acceptance request. Retain unaffected evidence with its original version and scope; software, direct-worker and native workflow evidence remain distinct. Recheck only source-sensitive evidence affected by the change, and finalize the hierarchy only after complete A/B reports and root approval. Report verified coverage increments and concrete blockers.

## Joint UI finish

After the requested rounds pass, A, B and C review frontend clarity, flow, consistency and visual quality together. Choose a bounded set of concrete changes, implement them, then inspect the actual UI in supported themes/layouts/font sizes. Recheck affected interactions and preserve the accepted scientific/execution boundaries. Summarize the resulting user benefit and material remaining limitations. Any final UI edit changes the application fingerprint: create a new bounded readiness audit or explicitly rerun affected source-sensitive checks before calling the final package validated; do not relabel an earlier frozen-source receipt current.

For navigation changes, verify the lifetime of the actual editor, Agent and terminal nodes as well as screenshots. A hidden child still remounts if a parent error boundary is keyed by route. Keep the current editor outside that boundary; test delayed save acknowledgements across conversation changes without replaying failed writes on mount. State shared within one renderer is not a cross-window transaction mechanism.

For monitoring changes, distinguish reading saved job records from observing the scheduler or process. Keep local and cluster availability separate; retain original states and observation times on failure. Do not display a live zero before the first successful read. Bound each read source independently, including nested log viewers, and verify that disconnect/reconnect cannot append stale or duplicate log chunks. Recovery of a worker connection does not prove offline model access or a local copy of complete chat history. A desktop transport that is not currently attached does not establish that the original worker daemon is offline. Reuse its exact recorded source and a bounded read-only health check before classifying the prerequisite; never reinstall or update an existing source merely to test a UI entrance.


## Human handoff and interrupted native control

An automatic goal continuation is not explicit permission to resume computer control after a physical Escape stop. Continue already-authorized non-UI source, package and evidence work when appropriate; keep UI acceptance pending until the user explicitly resumes. Never treat a user acknowledgement as proof that a file was actually selected: verify the displayed target and scope before reading or changing it.

Show paths intended for a human system file picker inside a literal code span/block. Preserve separators before dot-prefixed directories; a Markdown-escaped path and a missing file are different failures. Check the actual chosen/displayed path against the existing public test fixture, and do not attribute an instruction-formatting error to product file handling.


A DOM dialog count of zero does not establish that a Windows native file or confirmation dialog closed. Verify native modality and the completed operation's actual result before dispatching another action to the owner page. Do not click through an unresolved native modal via Playwright simply because the underlying DOM button remains enabled. A pending or stale post-key snapshot is not cancellation/saving success; retain the uncertainty rather than replaying Save or opening a second request.
