# Find a scientific tool

Start tool lookups from the internal release inventory. Call `search_software_docs({})` and match the advertised names or aliases. A name or version lookup stays local by default, including when the inventory has no match. Rows identify the repository, reviewed commit, release integration status and related `guidance_functions`. `source_only` identifies an upstream source and guide. `native_adapter` indicates that at least one related function has built-in execution support. The same rows are under **工具与资源 → 算力与管理 → 第三方工具包 → 随版本收录的源码仓库**.

Read the relevant function with `read_scientific_skill`, then request its needed reference by the exact advertised `document_id`. Cite the bundled documents actually read, and identify any detail they leave unverified. Distinguish the catalog's reviewed revision from any different source revision recorded by a bundled reference.

To fill a gap or cross-check the internal guide, use `read_software_docs` for the returned `guide_url` at the reviewed commit. Internal and public lookups may run in parallel. Compare sources and revisions. For scientific evidence use `search_scientific_literature` and read the relevant public paper or abstract. For explicit offline or internal-only requests, stay with internal sources and report the gap. Set `sources="public"` with a software name for live GitHub and PyPI results. This can run alongside the local lookup. For a registered checkout, use `list_source_projects` then `inspect_source_project` with its advertised ID when available. For pyGAS use authorized shared sources and the specific CV, bias or analysis route. Verify target readiness from its own installation and test evidence.

For a lookup, explain what the program takes as input, what it produces and which integration exists. Use `scientific_skill_catalog` for the AIMatterLab function and `describe_engine` for an advertised worker engine. A release entry establishes source identity. Installation, operation on a particular target and scientific accuracy each require their own evidence. For HotHam's Hamiltonians, dataset/training/inference cases and concrete acceptance criteria, read [the HotHam reference](references/hotham.md) by its advertised document ID.

When asked to install or verify a tool, identify the selected version, target and intended function. Check the environment and any existing execution skill before fetching a second copy. For a configured target use its bound execution skill for daily operation and its scoped grant for archived setup or repair guidance. Public source lookup supplies product information and preserves these access boundaries. For a new target read the install instructions for that revision and use the declared inputs, dependencies and example for that function. If the target is missing and changes where software will be installed, ask which resource the user wants. A lookup alone needs no installation or job submission.

- **Hosted SSH resource.** Read `cluster.resource-tools` and its `references/resource-tools.md`. Use the acquired resource’s inventory and its existing execution skill if available. For new setup, prepare the requested function, pinned source or reviewed script and a bounded test in `plan_resource_tool_setup`. The desktop reviews the draft and executes it. Check the original `setup_id`, test job, outputs and resource-scoped execution skill via the returned identities.
- **Local/WSL target.** Inspect the selected runtime and reuse its versioned environment. When authorized and the target exposes command execution, follow the upstream install guide and run the chosen example in a fresh working directory. A registered dedicated adapter also has a current environment/engine probe. If the chat lacks a required installer or terminal capability, give the exact next action for that target. The desktop's packaged CPU configuration wizard currently operates the reference `installation.check` case.
- **Package or source inspection.** The desktop's **选择并检查工具包** accepts a packaged directory with `tool.json`. A source checkout with an `aimlab-tools/manifest.json` declaration has a separate source inspector. From an authorized AIMatterLab source checkout, `node scripts/check-aimlab-tools.mjs --repo <tool-repository> --commit <sha>` checks that declaration. Registration and definition inspection record the declared interface. For an explicitly selected registered delivery skill, read its advertised `selected.managed` document IDs for additional instructions.
