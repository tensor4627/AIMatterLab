# Verify product behavior against its source

Identify what the user observed, the desktop build (**设置 → 软件更新 → 当前版本**), the provider or tool involved, and which resource or job service returned the result, as relevant. The desktop and a connected worker can run different builds. A screenshot can establish the visible label, a catalog the declared feature, and a run receipt the action that actually occurred.

Start with the supplied documents, bundled guides and release inventory. Where evidence is incomplete, use the matching authorized checkout or find the installed version's tag or source revision in the [AIMatterLab repository](https://github.com/tensor4627/AIMatterLab) or its [release history](https://github.com/tensor4627/AIMatterLab/releases). File names below are relative to that checkout. A link to `main` is a way to locate the owner. Verify the same file at the target revision before using it to explain an installed build. For a bug report, link to `https://github.com/tensor4627/AIMatterLab/blob/<commit>/<path>#L<line>` once the revision and line have been checked.

| Question | Read at the matching revision |
| --- | --- |
| Where is a page, or why is an action disabled? | `frontend/app/App.tsx` wires pages and actions. `frontend/app/workspace-shell.mjs` groups tools. Follow the rendered component under `frontend/features/` and inspect the action's enablement conditions. `frontend/features/workflows/workflow-catalog.mjs` declares the scientific cards, task templates and planned entries. |
| Why does chat find, omit or refuse a guide? | `agent/context/AGENTS.md` is the shipped runtime index. `agent/skills/scientific-skill-map.json` binds functions to skills and references. `scientific-skill-router.mjs`, `scientific-context.mjs` and `project-skills.mjs` in that directory implement reading, per-turn selection and private scopes. Inspect `agent/sessions/` and `agent/providers/` for the turn/provider in question. |
| What is advertised for an outside tool, and what can run? | `installation/tool-sources.json` supplies upstream sources and advertised integration. `contracts/tools/tool-package.schema.json` declares the portable package shape. `frontend/features/tools/ToolPackagesPanel.tsx` and `backend/main/tools/package-registry.mjs` own the versioned package and its receipt. `backend/main/compute/resource-tools.mjs` and `frontend/features/tools/ResourceToolSetup.tsx` own per-resource setup. For a native adapter use `contracts/tools/engine-contracts.json` and the implementation in `backend/worker/studio_worker/tools/`. The user-facing lifecycle is in `docs/software-specification.md`. |
| Which service owns the result? | `desktop/main.mjs` and `desktop/preload.cjs` connect typed UI requests to the main process. `backend/main/compute/` coordinates target selection and leases. `backend/main/workspace/` manages workflow drafts and deployment. `backend/worker/studio_worker/transport/mcp.py` defines worker-facing tool contracts. `compute/` and `workspace/` inside that Python package own job lifecycle and calculation files. |
| Was this behavior tested? | Find the matching check under `tests/agent/`, `tests/frontend/`, `tests/integration/` or `backend/worker/tests/`. Read `docs/releases/` for that version's observed results, scope and pending checks. Useful entry points include the [architecture](https://github.com/tensor4627/AIMatterLab/blob/main/docs/architecture.md) and [developer package guide](https://github.com/tensor4627/AIMatterLab/blob/main/developer/README.md). |

With an authorized checkout, inspect the owning files and report the relevant revision and behavior. Fill gaps or cross-check the local evidence in parallel through public web search or `read_software_docs` at a versioned public text URL, for example `https://raw.githubusercontent.com/tensor4627/AIMatterLab/<commit>/frontend/app/workspace-shell.mjs`. Use only public names and paths for web reads. If the user explicitly restricts research to internal or offline sources, report any gap using the internal evidence. If source is inaccessible, give the version-specific file to inspect and identify which behavior remains unverified.

An upstream scientific API question has a different owner. `list_source_projects` and `inspect_source_project` cover registered public scientific catalogs and advertised symbols. For an environment-specific API, use the selected environment's `inspect_environment_api` where available. For HotHam use the bundled `software.catalog` reference, and the versioned upstream guide to cross-check the answer or fill a gap. Keep the desktop checkout, an upstream package and the executable actually loaded on a target distinct in the diagnosis.
