# Parameters, evidence and review

Preserve the user's temperature, ensemble, CV intent, atom choices, model and run scope. In a continuation, update only the requested choices and their dependent inputs. Use the following order to fill missing non-file scientific parameters.

1. Use the selected engine's contract, version-matched manuals and inspected inputs. Derive atom count and order, topology candidates, PBC, CV dimension, units, signatures, dtype, output basenames and capacities from their actual sources. Keep the basis for inferred values and verified defaults.
2. If the first pass leaves a value uncertain, or the user asks for research, use `search_scientific_literature`, `read_software_docs` or available public web search. Honor offline and internal-only requests. Use public terms in queries and read the relevant source before selecting a value. Compare material and phase, model, ensemble, units and engine version where they affect applicability. Cite the source and conditions for a value chosen from research.
3. If the evidence is still insufficient, or an unavailable lookup leaves the value uncertain, leave it unset in `parameters`. Include its typed field and units in `steps` and its key in `missing_fields` so the user can fill it directly. Continue independent preparation. For a consequential choice such as a reaction coordinate, atom mapping, thermodynamic state or potential, state the remaining decision and ask one focused question if needed. Identify conflicting procedures when personal and bundled guidance disagree and let the user choose.

When the user delegates an example, a reversible pilot setting can be proposed with its reason, source and limited scope. Label it for review. Keep unresolved production choices open and tie duration, stability, accuracy, FES convergence and data availability to their own evidence.

Start from one natural-language goal and produce a mostly complete proposal, not a questionnaire. Put the few system/task-dependent basic parameters and unresolved decisions first. Group secondary settings by purpose below them and fold large groups into secondary menus. Show a concise summary of consequential choices and their basis so a novice can confirm and adjust them; do not make the user audit every technical parameter individually. Technical details remain inspectable, with source/proposed/derived status, without occupying the primary review path.

When public interface evidence is sufficient for the authorized authoring stage, save the reviewable driver and record unexecuted dtype/ABI and target-runtime checks as execution-stage `not_run`; do not treat a test that has not run as another missing constructor contract. A genuinely missing target API is a concrete software-tool gap to report, not permission to guess scientific conditions or bypass pyGAS.

`parameters.validation` is a reserved numerical-test namespace: use only the exact `validation_controls` keys returned by the selected engine contract. Runtime status, validation scope, artifact claims and missing-information diagnostics are descriptions or a separate saved review manifest, never editable engine controls. Do not make an empty diagnostic array a required scientific input. An absence of unresolved scientific questions belongs in `missing_fields=[]`, not a new empty form field. Actual checks and run receipts supply validation evidence; authorization alone is not a passed check.

Completing `bias_file`, `structure_file`, CV dimension, cutoff and mode from inspected files/definitions is Agent work, not a request for the user to learn wrapper API names. Infer only when there is evidence; a conflict or absent physical choice stays explicit. Describing an engine discovers its machine contract, not its runtime capabilities or serialized-model compatibility. Do not call preparation/validation/submission tools during a v2 science review to work around missing contract information.

Use `present_task` to publish the saved input paths and readable fields. Keep `parameters` for actual scientific/engine controls and required input paths. Put evidence, source provenance, file hashes, validation scope and status in step descriptions or a saved, clearly named review manifest; do not create editable `review`, `provenance` or `source` parameter trees, `*_sha256` fields or free-text `*_source` audit notes. Review is not a request to restate the same measured fact under new parameter aliases. Preserve the current scientific keys and values when nothing changed. A changed review note or manifest is not proof that a scientific input was updated; never add comments or change an unrelated file hash to evade a stale-input gate. Put structure/model, physical conditions, CV and essential bias settings in workflow order. Group secondary controls under `advanced:true`. Include `default` and `default_source` only when the default is verified. Keep `label` a stable parameter identity, never a temporary claim such as currently empty, awaiting selection or not yet assigned. Use field `description` for enduring meaning, units, valid ranges and assumptions; use `default_source` only for the verified software/version/schema/function reference, not current-value or missing-state promises. Put transient planning observations in recorded step notes; the UI computes current values and missing status independently. Do not put source code, full provenance records or raw graph objects into the mandatory editable form; keep their saved file paths and a compact description.

Serialized artifact loading, real-neighbor force checks, target-environment compatibility and an actual bounded engine run are separate evidence and are never implied by authoring success.
