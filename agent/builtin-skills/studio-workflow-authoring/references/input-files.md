# Files, assets and target APIs

Use `find_local_input_files` for a desktop directory explicitly named by the user. Use `import_workflow_input` with the exact supplied or discovered `local_file`, or with a direct public HTTPS `url` selected for the task. Both import paths write to the current authoring worker, including a remote SSH worker. Respect offline requests and check the purpose and format before using the file. For a file already on the selected SSH worker, use `copy_project_inputs` with its exact path. Use the returned saved path in its named `file` or `files` field and in `parameters.files`. Check required engine basenames and actual config references. Use the optional import `name` or the SSH copy `names` when a file already in the correct format needs a different basename.

Author required control inputs such as GPUMD `run.in`, NEP `nep.in`, `GAScfg.yaml` or a PyDyn `run.py` from the user’s calculation request. Use `describe_engine`, the matching software documentation and the verified input assets to map each resolved value to the actual command, key or API argument and its unit. Generate files for the chosen version with `write_project_input`. Read each saved file back and bind its path as a `file` field and in `parameters.files`. Keep pending decisions visible as editable fields. When a confirmed parameter changes, update affected control files with their current hashes and reread them before publishing the updated paths and values.

The desktop supplies an authoritative authoring workspace. Use its project and candidate environment for the tools that need them. An old empty project list, `Unknown project` response or read-only shell sandbox in history is not evidence that the current structured authoring tools are blocked. If the current workspace acquisition fails, report that exact failure; do not ask the user to invent an internal project ID or output path.

Inspect the actual source/catalog and structure before writing scientific inputs. Use `inspect_asset` for ASE structures or datasets, not Python, JSON, configuration or binary model files. For files in a user-specified directory on the selected compute resource, call `copy_project_inputs` with the workflow’s `project_id` and a single `sources` list of exact absolute or ~/ paths. It makes independent copies in the current workflow draft or named workspace and preserves relative filenames. A manual import or extra source-root grant is unnecessary. Use the returned copy paths for subsequent inspection and edits. Read saved project input text and model metadata with `read_project_input`; it needs no Windows/WSL shell, does not deserialize binary models, and returns an actual SHA256. Use the available structured source, asset, ASE and parameter-suggestion tools, then save actual structure, graph, Python and engine configuration files through the authoring tools. Renderer-returned paths identify saved inputs. Do not paste executable code or graph JSON into an advanced form field as a replacement for a file. Never claim a save from a proposed path alone.

For a new planning workflow whose engine route is still empty, first call `present_task` with the SAME supplied `studioTaskId`, honest draft steps/missing fields, `parameters.engine` and the actual current `parameters.files` (empty only when no inputs exist). Preserve existing scientific values, manual edits and stable step IDs; never replace a nonempty different route automatically. This scaffold is a saved draft, not completeness review or execution permission. Bind that route before the selected-environment API read; do not create another task or change the authoring environment to inspect a target.

For `pydyn.sampling`, derive driver calls from the explicitly selected registered environment. When available, use `inspect_environment_api` with that environment ID and engine to read its partial API index, then request only needed advertised `api_symbols`. A global `inspect_source_project` result describes its registered source, which may differ from the compute version; a runtime guide supplies observed identity, not complete API bodies. Missing target API evidence needs the matching environment check or a concrete capability report, not a silent source switch, reinstall, arbitrary file-reader workaround or invented interface. This read does not change the authoring environment or execution grants.

Read `describe_engine` for the chosen registered engine, or the current `engine_contracts` supplied by the desktop workspace. Use the actual required input basenames, canonical adapter parameters, allowed aliases and mode values. Build the human-readable fields from that contract and the user's scientific facts. Match file parameters to actual `files` entries; preserve basenames such as `run.py`, `run.in`, `model.xyz` and `GAScfg.yaml`. A nested visual field and its flat adapter alias must agree; do not invent a second value to silence a preparation error.

Use the supplied current parameters, manual edits and task ID. Stable step IDs keep the page understandable across turns. Before changing an existing generated file, use `read_project_input` to read its current text and SHA256. Update its project-relative name with `write_project_input`, passing that hash as `expected_sha256`; renderer subdirectories such as `cv-<id>/build_bias.py` are valid owned relative names. On a hash conflict, re-read rather than overwriting newer edits. Read the saved file back, compare the returned hash and intended scientific values, and only then publish the active paths through `present_task`. Keep renderer source and graph paired; do not leave an old active reference or make an untracked top-level copy just to evade a nested-path failure. Save changed `run.in`, driver, graph or configuration files before publishing the new parameters: changing a form value alone does not update an already saved engine input. Do not create a second workflow unless the user explicitly requests it.

For run assets explicitly selected by the current user and within existing authorization, use existing artifact-read and project text-save tools to place a bounded UTF-8 text copy in the current project's usable workspace or authorized input roots, preserving content and line endings and comparing the read-back SHA-256 with the source; if byte equality or access cannot be established, retain the reason and use normal desktop import without fabricated hashes, broader grants or shell bypasses. For exact user-selected binary or text inputs on the workflow’s compute resource, use `copy_project_inputs` and verify its returned paths and hashes. For assets on another resource use the available authorized transfer or desktop import; the absence of a generic binary importer must not block feasible text handoff. Before publishing a reviewable workflow, complete these mechanical file bindings and check that actual calculation inputs belong to usable authorized roots without changing scientific parameters; saved inputs, optional review, execution state and actual validation evidence remain distinct.

A future `bias.pt` belongs to its producing build stage. List the saved inputs and bind the output to the supported consumer stage. For an existing serialized artifact use its actual identity and target checks. In a local execution graph, `gpumd.md` and `trajectory.density` have registered port contracts. Other invocations need a supported execution path before promising end-to-end execution. A missing force field can leave MD pending while CV or structure authoring continues.
