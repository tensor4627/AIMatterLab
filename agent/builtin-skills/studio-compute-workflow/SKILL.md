# AIMatterLab compute resources and jobs

For new installations, existing submission scripts, or a resource-private tool, read [resource-tools.md](references/resource-tools.md) through `cluster.resource-tools`. For the confirmed resource root and the current conversation's actual work directory, read [base-workspace.md](references/base-workspace.md) through `cluster.workspace-setup`.

Ordinary chat can use an authorized compute resource, inspect queues, configure an environment and submit an explicitly delegated independent job. Recommend the planning workflow for reusable multi-step calculations or when the user wants a visual review. Update an existing workflow in place when its scientific inputs change. Follow the latest user request, current tool schema and receipts. A planning checkbox or a skill never confers access or execution permission.

## Use an already authenticated resource

1. Call `list_compute_resources`. AIMatterLab lists hosted SSH resources after verified login. At first use, the user signs in privately and selects **登录完成，交由 AIMatterLab 管理** in its terminal. For a general cluster query with one eligible SSH resource, use that resource. A name in the original request or a short follow-up such as “就是<name>” selects the matching listed resource. Use its returned `resource_id` to continue the original request in this chat. `resource_selection_required` concerns choosing a target. Selecting a hosted resource in chat requires no desktop panel binding. Report any genuine access or login issue only from its own tool receipt.
2. Call `acquire_compute_resource` using exactly one selector (the resource ID, profile ID or the alias the user named). For an unfamiliar nickname, pass it as `alias` so the confirmed mapping can be saved to personal skills. Choose `access: "service"` for queue probes and a registered job service. Choose `access: "terminal"` for private shell work. DeepSeek presents eligible `choice_required` candidates in the chat input area and waits for the user's selection. For a `target_selected` receipt, follow its `retry` with the requested access to continue the current task. Use a supplied `user_answer` to continue the discussion. When a provider returns unanswered `choice_required` candidates, ask which one in this chat. Include the listed `resource_id` or `profile_id` for duplicate display names. Wait for `acquired` before reporting a lease. `canAcquire`, ready service and free terminal slots are eligibility and availability observations. `verification_pending` concerns the worker project access check. Only an acquired terminal with its session receipt establishes a shell.
3. For live queues, first acquire service access to the same resource and call `inspect_compute_service` with the returned `resource_id` and `probe_scheduler: true`. The service lease grants no shell. If the service probe is unavailable and a terminal can do the requested read, use a returned terminal lease on that resource. Its tools are `list_compute_terminals`, `read_compute_terminal` and `write_compute_terminal`. Send `type` and `enter` separately and check `output` and `exit_code` in the `enter` receipt. Use [compute-discovery.md](references/compute-discovery.md) for Slurm and LSF observations.
4. Report the observation time, scheduler, eligible queues and available device capacity actually established. Use the user's personal skill or confirmed private policy for ownership, order, allowed queue/account/QOS and cost. Verify current idle resources with the scheduler. Queue or node visibility alone cannot establish access, ownership, price or usable GPU capacity. Keep private facts in the conversation and local configuration.

## Recover the original SSH connection or channel

A submitted option such as **Use “Lab” (ssh:profile-id)** selects that listed target for the current conversation. Continue the requested acquisition with its resource ID and access. The same rule applies to the dedicated resource picker. An answer that only requests a plan leaves the terminal unopened.

If a terminal request returns `terminal_unavailable`, use the reported `code` and `leaseStatus`. Follow its `retry` with `access: "service"` on the same resource when the requested operation can use the service. A failed or unconfirmed terminal attempt provides no shell. Preserve unknown state and avoid repeating the same terminal attempt. If no safe retry or suitable granted channel remains, report the actual tool failure. A channel failure alone calls for checking the original capability. Use the current tools when old chat messages or guides describe a different route.

Open or refresh the original saved SSH profile to check its current connection. Reopening a live SSH terminal restores the same verified channel. If the original sign-in is pending, continue that attempt. The user can view its prompts and enter authentication responses only in the private terminal. Waiting for authentication or a timed-out check leaves the outcome unconfirmed.

While the saved profile shows **等待登录回执**, the desktop looks for the terminal with that sign-in request ID. The user can choose **重试** to retrieve the same attempt. If the hosted connection is confirmed lost, the user can choose **重新登录** on the same saved profile. The desktop verifies the remote host, account and workspace and restores eligible leases for their original conversations. Read the current resource and terminal receipts. If the user explicitly requests renewal, use the verified selection saved for this chat. Reconcile an unknown attempt or existing job using its original run and scheduler identities before any further execution.

Manual sharing applies only when the user explicitly shares an existing visible terminal. Use `list_shared_terminals`, `read_shared_terminal` and `write_shared_terminal` within that actual grant. For explicit service setup or repair use the `cluster.connection-setup` route for [job-service-connection.md](references/job-service-connection.md).

## Configure the environment in the current scope

Use `compute_readiness` and `discover_local_environments` when available for registered local environments, bounded discovery and observed CUDA capabilities. Reuse the actual interpreter, executable and pinned source version. Discovery gaps and version warnings limit claims about specific operations. Inspect and repair the selected environment in its own authorized shell. Offer `draft_local_environment` or `draft_cluster_setup` when available and relevant, with observed values for review in settings. Use the connection editor for user-owned credential, project and resource-limit changes. Preserve existing registrations and engine branches.

For cluster workspace setup on the selected job-service path, read [base-workspace.md](references/base-workspace.md). `setup_base_workspace` may inspect or initialize the active service's base authoring directory when advertised. For explicitly requested directory or environment setup in a hosted shell, use an acquired terminal lease and the user's actual path and scope. Verify the result on that resource. Reuse the original directory for a saved workflow. Installing software, probing a compute node and submitting a job each require scope covering that operation.

For scheduler adaptation, use the user's selected successful templates if needed to resolve site-specific settings. Inspect them as data. Verify the actual scheduler, resources and activation separately. Use [compute-discovery.md](references/compute-discovery.md) for adaptation and [profile-format.md](references/profile-format.md) for a private profile. Keep hosts, queue names, local paths, private templates and receipts out of shared instructions.

## Prepare, run and observe the requested calculation

- For a visual workflow, reuse supplied structures, potentials, scripts and outputs. Resolve the missing scientific choices and edit its existing parameters and real files. Keep resource, environment, scheduler and wall-time choices in deployment. MetaD and WTMetaD use one run and one walker unless the user requests a supported replica/shared-state mode. Consult [scientific-gates.md](references/scientific-gates.md) for the selected engine.
- For a worker-managed independent job, call `inspect_compute_service` on the acquired resource. Use an authorized environment for `kind: run`, or the authorized cluster and resource limits for `kind: cluster-run`. Pass the real inputs, engine, `max_seconds` and a stable `spec.idempotency_key` to `prepare_compute_run`. Its receipt returns `id`. Use that value as `run_id` with the same `resource_id` for `validate_compute_run`, `submit_compute_run` and subsequent observation. Submit within the user's execution request and actual limits. For a run linked to a reviewed workflow, follow its reviewed execution path. Honor draft-only, no-build, no-run and stop requests.
- For an explicitly requested job using a user-provided site script on a hosted SSH lease, verify the exact script, target and applicable site permissions. Submit via the selected scheduler using that conversation's shell. Read its real scheduler job ID and report the submission separately from worker-managed runs. Respect the real limits and preserve receipts. A terminal lease does not expand project or file authorization.
- Use `read_compute_run_status` and `read_compute_run_log` for the exact acquired resource/run when available. Use the original worker tools for a legacy worker run and the specific scheduler job ID for a site-native job. After an uncertain submission or cancellation, reconcile the same job and attempt before any retry. [reconcile.md](references/reconcile.md) covers observing existing recorded worker runs and collecting their artifacts.

Report submitted, queued, running, exited and scientific validation from their corresponding evidence. Check the real target and serialized bias artifact for sampling. An explicitly selected AOTI artifact must fail if incompatible. Preserve actual run state and hashes. Collect the requested outputs through the bound transfer route and verify their receipts.
