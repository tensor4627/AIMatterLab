# Local / cluster job-service connection

Use this flow when the human requests AIMatterLab service setup, including a terminal login that is not yet ready for workflow tools. First identify the selected saved connection and current status through the available typed AIMatterLab interfaces. A live shell, successful SSH authentication, a configured profile, service health, project authorization and scientific validity are distinct evidence.

## Local WSL

Select the saved WSL distribution and service root. Prefer the explicit existing service/interpreter environment; discover bounded existing Conda/venv interpreters before proposing installation. Use AIMatterLab's local connect/setup entry and observe the actual service identity and tools readiness. Keep the service interpreter separate from the registered Python used by each scientific engine. A local service connection does not approve project paths, engines, GPUs or execution limits.

## Interactive cluster login

1. Use the exact saved connection and version selected by the human. The human types passwords, MFA and host trust in the AIMatterLab terminal; those bytes never enter Agent tools. AIMatterLab proves the original authenticated OpenSSH process and its private control socket, then automatically presents an ordinary shell on that same connection. Ordinary login does not require a remote probe command, a particular banner, or an exact remote user-name print. Service identity and health are verified separately. No extra manual confirmation or second login is required in the normal flow. If a completion receipt is unknown, observe the same original request without replay; only the human may explicitly continue it. Successful login opens only the ordinary terminal. The human’s **交给 Agent** click is the trigger and authority for remote service inspection, first worker setup/registration or verified cached reuse on that selected connection. After service verification, grant that same conversation service access without an extra service-authentication screen. Unsupported service-channel capability must not hide the explicit ordinary SSH terminal option. Review a supported WSL/Linux client and key namespace when needed; never silently rewrite a saved Windows client, key or route or open another SSH login as a fallback.
2. Before starting the service, inspect the original terminal and any existing environment only within the authorized setup scope. Prefer a saved interpreter, an existing Conda/Anaconda environment, venv or site module. Missing `python3` on PATH does not prove Python is absent. Do not scan unrelated research trees or expose connection details.
3. Verify the chosen interpreter's actual version and `sqlite3` import using a bounded check. Use the minimum version established by the shipped worker and loader, rather than imposing the scientific engine's Python requirements. Distinguish unsupported version, missing SQLite, missing executable, activation failure and unconfirmed communication. A version print alone does not verify the job service.
4. Propose the observed absolute interpreter path and only the activation commands actually needed. Examples of recipe shapes are `source <conda-root>/etc/profile.d/conda.sh` followed by `conda activate <existing-env>`, `source <venv>/bin/activate`, or a site-provided `module load` command. These placeholders are not runnable configuration; substitute observed, user-selected paths. Do not modify the base environment, install a new interpreter, switch engine branches or submit a scheduler job without that scope being authorized.
5. The human saves the recipe in the selected connection's **作业服务环境** fields under **连接计算资源**. Saving uses the human-only versioned connection editor. The executable recipe is private local configuration; its derived per-connection `SKILL.md` records the connection/version and non-secret guidance. Do not put activation script bodies, passwords, tokens, hosts or queue information in distributed skills or global skills. A derived skill is documentation, not authority to change connection settings or project permissions.
6. First setup begins only after the original terminal has been handed to Agent and a real current conversation exists. AIMatterLab applies the saved environment through that authenticated connection's private service channel and verifies the real service identity, version, directory, port and health before persisting registration. Record incomplete tool inventory as a warning rather than blocking setup. Keep the interface and cache available so the human and Agent can choose and configure scientific tools later. Ordinary shell input and history remain available between serialized exchanges. Registration never stores SSH authentication, an active session, an Agent grant or project authorization. Explicit update, environment repair and scheduler configuration remain advanced connection settings; ordinary use has no extra setup screen.
7. On a later login the human completes authentication again, explicitly selects the connection, then clicks **交给 Agent** once; only then check and reuse the registered service for that conversation. Daily reuse verifies the pinned cache/host/runtime/health without reinstalling or upgrading the worker. Refresh the real tool inventory with a nonblocking warning if it is incomplete; this does not establish scientific environment readiness. In that explicit handoff, a definitely stopped listener may start the same fully verified cached worker once; timeouts, identity errors and unknown requests never authorize restart or replay. A missing or corrupt cache or changed identity needs explicit maintenance; process liveness or prompt patterns never prove authentication. The combined handoff grants both verified capabilities; the backend continues to bind each grant to its exact channel and context. Unknown channels are never automatically reconnected or replayed.
8. **检查当前服务通道** reads authenticated health and tool inventory without bootstrap. **更新作业服务** is separate explicit maintenance of the service channel. Interactive handoff now reuses the exact granted shell for bounded, serialized worker exchanges. It does not require the gateway to accept another exec channel. Each exchange waits for confirmed shell readiness, uses verified cached worker code after initial setup, and confirms the original shell has resumed before ordinary input is released. Raw terminal writes, resize and owner changes queue behind the exchange; reads expose only public output. A busy foreground program receives no protocol command. Do not quietly choose another host, interpreter or scientific environment. Never turn an unknown occupied PTY into a usable shell by clearing its protocol lock. The supported serialized path keeps that lock until its exact restoration barrier; it does not claim simultaneous raw input.
9. Report service readiness only after connected/workflow-ready evidence. Service-use and shell-input grants are verified independently but enabled together by the normal handoff. **我来操作** reclaims both grants belonging to that combined handoff without stopping the service channel or worker. Closing a shell does not close the service or master; stopping the service does not stop the shell, master, worker or jobs. Ending the whole SSH connection revokes its temporary channels and grants while preserving registration and actual jobs. Project authorization and engine registrations remain separate. Never infer scheduler permission, GPU availability or scientific validity from login-node service success.

## Inspect the service already selected by the human

For questions about the currently connected cluster, call `inspect_compute_resource` before concluding that no resource was shared. It reads the selected connection, actual verified service and current-conversation service grant without requiring a scientific workflow. The independent shell has its own state and grant; never infer shell permission from service permission or vice versa.

`list_clusters` lists saved scheduler configurations inside that service; it does not list SSH login sessions. Empty `list_clusters`, `list_projects` or `list_workflows` results do not mean that the user has not logged in or handed over the service. Do not ask the human to authenticate again, share another terminal or create a replacement workflow to fix an empty registration list.

When the user asks to inspect queues, call `inspect_compute_resource` with `probe_scheduler: true`. Its negotiated bridge capability performs only fixed, bounded Slurm/LSF observations on the already authenticated login host. It does not require a scheduler registration, send input into the protocol terminal, open another SSH connection, register a profile or project, or update the pinned worker. Report actual observation time and `observed`, `not_found`, `command_failed`, `timed_out`, `output_limit` or `invalid_output` results. Visible queues, node states and GRES descriptions do not prove compute-node GPU availability, execution permission, ownership, price or scientific validity.

If the current bridge returns `requires_new_attachment`, preserve the other channels and explain the missing capability. A human explicitly stops and reattaches only the service channel to load the shipped bridge; never reconnect the master, stop a shell, upgrade the worker or replay requests automatically. Service registration and the installed worker remain separate from this transient bridge capability.

Saving a Slurm/LSF submission configuration is a later reviewed action in the current connection's **作业服务设置**. Use the observed scheduler and user-selected limits as evidence for that review, then use its saved identity for `probe_cluster` and subsequent deployment tools. Queue inspection alone never authorizes project access or submission. Record isolated protocol tests and actual cluster observations separately; local fake schedulers are not evidence about the user's real queues.

## Failure and return to terminal

Use read-only status checks first. If the service was definitively rejected locally before dispatch, leave the SSH terminal available and show the local failure. If a start may have been sent, preserve the exact connection and attempt: a later idle observation alone cannot rule out an in-flight request. Stop only that private service channel with its exact attempt fence. The separately verified ordinary shell remains usable. A historical single-PTY session must retain its protocol lock until its own shell-restoration proof; never unlock it to imitate independent channels. Unknown state never authorizes automatic bootstrap, request replay, resubmission, or typing into a possibly occupied channel.

Stopping the service keeps its saved registration, the remote worker/run state and the ordinary shell. Shell input and service use keep separate human/Agent grants; handing over either capability does not recapture the other. The human can explicitly reuse the registered service through connection settings. Ending the entire SSH connection removes its transient channels and grants. A fresh login can reuse the persisted service registration after the new login is actually verified.

Keep private recipes and diagnostic receipts in ignored local storage. Record `passed`, `failed`, `blocked` or `not_run` for interpreter availability, activation, service handshake/identity, workflow tools and scientific execution separately. Do not promote a compatibility test or isolated fixture to evidence about the user's real cluster.

A failed Python/service preparation leaves the already shared ordinary shell available. Read its derived per-connection environment guide and use that same shell for an explicitly requested repair; do not ask the human to repeat login or go through another service-authorization workflow. Do not infer that sharing the terminal alone proves worker readiness: report actual service errors and keep scientific execution approval separate.
