# Studio workflow authoring

Use the current interaction mode and conversation-owned task ID. Ordinary chat does not create files or a workflow. In planning and workflow review, prepare the concrete inputs while leaving execution to the desktop's human gate. Never run builds, MD, training, evaluation or scheduler submissions through a skill or shell to make a draft appear complete.

## Own the authoring work

The desktop supplies an authoritative authoring workspace. Use its project and candidate environment for the tools that need them. An old empty project list, `Unknown project` response or read-only shell sandbox in history is not evidence that the current structured authoring tools are blocked. If the current workspace acquisition fails, report that exact failure; do not ask the user to invent an internal project ID or output path.

Inspect the actual source/catalog and structure before writing scientific inputs. Use `inspect_asset` for ASE structures or datasets, not Python, JSON, configuration or binary model files. Read saved project input text and model metadata with `read_project_input`; it needs no Windows/WSL shell, does not deserialize binary models, and returns an actual SHA256. Use the available structured source, asset, ASE and parameter-suggestion tools, then save actual structure, graph, Python and engine configuration files through the authoring tools. Renderer-returned paths identify saved inputs. Do not paste executable code or graph JSON into an advanced form field as a replacement for a file. Never claim a save from a proposed path alone.

Separate three kinds of input:

- **Supplied scientific choices:** preserve the user's temperature, ensemble, CV intent, atom choices, model and run scope. A continuation changes only the requested choices and their dependent inputs.
- **Discoverable technical facts:** derive atom count/order, topology candidates, PBC, CV dimension, units, signatures, dtype, output basenames and available capacities from real assets/source. Fill these yourself and retain concise provenance. They are not questions for the user.
- **Unresolved physical choices:** if the intended material/phase, force field, incompatible atom mapping or competing CV interpretation cannot be resolved from supplied assets, ask one focused question after completing independent authoring work. Do not replace an unspecified potential with an arbitrary model.

A reversible pilot setting can be proposed with its reason, source and limited scope. It must be visible for review; a technical source default is not evidence for a physical production parameter. Do not invent a production duration, stability, accuracy, FES convergence or data availability.

For molecular phi/psi, inspect the actual topology and the installed pyGAS torsion API. Report the selected ordered atoms and indexing convention. A molecule name is insufficient evidence for indices or sign; a coordination/distance example is not a torsion implementation. If topology yields competing assignments, preserve the candidates and ask about the scientific ambiguity.

## Connect the science to the real engine contract

Read `describe_engine` for the chosen registered engine, or the current `engine_contracts` supplied by the desktop workspace. Use the actual required input basenames, canonical adapter parameters, allowed aliases and mode values. Build the human-readable fields from that contract and the user's scientific facts. Match file parameters to actual `files` entries; preserve basenames such as `run.py`, `run.in`, `model.xyz` and `GAScfg.yaml`. A nested visual field and its flat adapter alias must agree; do not invent a second value to silence a preparation error.

Completing `bias_file`, `structure_file`, CV dimension, cutoff and mode from inspected files/definitions is Agent work, not a request for the user to learn wrapper API names. Infer only when there is evidence; a conflict or absent physical choice stays explicit. Describing an engine discovers its machine contract, not its runtime capabilities or serialized-model compatibility. Do not call preparation/validation/submission tools during a v2 science review to work around missing contract information.

## Continue the same page

Use the supplied current parameters, manual edits and task ID. Stable step IDs keep the page understandable across turns. Before changing an existing generated file, use `read_project_input` to read its current text and SHA256. Update its project-relative name with `write_project_input`, passing that hash as `expected_sha256`; renderer subdirectories such as `cv-<id>/build_bias.py` are valid owned relative names. On a hash conflict, re-read rather than overwriting newer edits. Read the saved file back, compare the returned hash and intended scientific values, and only then publish the active paths through `present_task`. Keep renderer source and graph paired; do not leave an old active reference or make an untracked top-level copy just to evade a nested-path failure. Save changed `run.in`, driver, graph or configuration files before publishing the new parameters: changing a form value alone does not update an already saved engine input. Do not create a second workflow unless the user explicitly requests it.

Use `present_task` to publish the saved input paths and readable fields. Keep `parameters` for actual scientific/engine controls and required input paths. Put evidence, source provenance, file hashes, validation scope and status in step descriptions or a saved, clearly named review manifest; do not create editable `review`, `provenance` or `source` parameter trees, `*_sha256` fields or free-text `*_source` audit notes. Review is not a request to restate the same measured fact under new parameter aliases. Preserve the current scientific keys and values when nothing changed. A changed review note or manifest is not proof that a scientific input was updated; never add comments or change an unrelated file hash to evade a stale-input gate. Put structure/model, physical conditions, CV and essential bias settings in workflow order. Group secondary controls under `advanced:true`. Include `default` and `default_source` only when the default is verified. Do not put source code, full provenance records or raw graph objects into the mandatory editable form; keep their saved file paths and a compact description.

A future `bias.pt` is the product of a reviewed build, not an external file the user must manufacture. List the saved build inputs and the pending build stage. If the current Studio workflow contract supports only one executable stage, expose that boundary and the required successor explicitly rather than advertising an end-to-end run that cannot execute. Missing force-field or reference data remains an honest blocker for its dependent stage; it need not block authoring an independent CV or structure.

Conclude with what was saved, what is ready for review and the smallest remaining scientific decision. `missing_fields=[]` establishes form completeness only. Serialized artifact loading, real-neighbor force checks, target-environment compatibility and an actual bounded engine run are separate evidence and are never implied by authoring success.

For pyGAS graphs, read `inspect_source_project.graph_contract` before assembling the graph: `_mode`, `_node_ports`, `_edge_endpoint`, then `validate_graph`. These are hash-bound excerpts from the registered renderer, not a remembered schema. Use its node kinds, required input/output/neighbor/collect nodes and structured node/port endpoints; use the actual class catalog for CV and bias signatures. Do not guess a graph shape, retry `type` in place of `kind`, or invent ports from Python argument names. The concrete `render_pygas_workflow` result is the graph check; source inspection alone never claims the graph or serialized model is valid. If graph_contract is blocked or unavailable, report that limit and inspect the explicitly registered source instead of inventing compatibility.

Before a graph build, use `inspect_source_project(symbols=[...])` for the exact public CV classes when behavior or output rank is unclear. It returns bounded actual method bodies, including helper methods, from fixed registered catalog files; do not use `read_project_input` on a source repository. Read `_reduce_expression` and collector shape semantics. A scalar CV such as the inspected two-atom distance must reach Collect as a length-one vector through an explicit supported shape adapter (for a scalar, `reduce` operation `first` reshapes without dropping information). Do not use `first` on a multi-component CV to silence an error or change its scientific meaning. Repair the same saved graph and regenerate matching source; do not replace a failing graph with unrelated handwritten source.

The Studio render wrapper also needs `graph.settings.atoms_path` for the actual authorized structure and `pt_path` for the selected artifact. It uses immutable run basenames and `workflow_path=workflow.json`; include the graph, source and structure in the task files. For version 2 TorchScript-only, set `artifact_formats=['torchscript']` and `deployment_backend='torchscript'`. Explicit AOTI or dual artifacts retain their selected formats and require actual compatible target/toolchain preflight, with no fallback. Rendering/source inspection does not prove serialized artifact load, tensor ranks or scientific correctness; the reviewed build and artifact checks remain separate.
