# AIMatterLab

Apply the product's weak-validation principle to every change. Give the Agent the minimum constraints needed for data safety and the user's delegated operation. Use built-in workflows, skills and task planning as preferred, reusable paths. An authorized ordinary chat can inspect queues, configure its environment or submit a clearly requested independent job. Justify each blocking check by the concrete data, permission, target, hard resource limit or irreversible duplicate side effect it protects. Present suggestions, optional setup and compatible version differences as guidance or warnings. Review both the recommended workflow and an authorized alternative through their normal entry points.

Keep scientific engines in sibling repositories unchanged. Engine environments are explicit, versioned registrations; never switch their branches automatically. Run inputs and validation evidence belong to untracked runtime directories. No fabricated job status, metrics, model access, or scientific validation. Bias gates must load the serialized artifact and check the real target environment. An explicitly selected AOTI artifact must fail on incompatibility without backend fallback.

The Electron renderer has no Node or filesystem access. All privileged IPC is typed, sender-validated, and routed through the main process. MCP tools cannot change project authorization. The worker owns run state; the desktop owns its index. Submitted jobs survive desktop closure. Never automatically resubmit an unknown run. Tests: Node protocol/security tests and Python worker lifecycle tests; real scientific checks are reported separately.

Release discipline: manage this repository with Git. Use https://github.com/tensor4627/AIMatterLab.git for development, pull requests and all pushes. Publish commits, tags and release assets only to GitHub. The owner manages the NJU GitLab mirror. For each version, add one brief bullet per user-visible change to CHANGELOG.md. Record validation scope and passed/failed/blocked/not_run results in its version document under docs/releases/. Keep raw evidence in ignored runtime directories. Create local release tags only after checking the corresponding package; never invent historical commits or push without authorization.

Before creating or publishing each version tag, including prereleases, review every bundled skill and its references, the scientific function map, runtime instructions and model-facing turn prompts. Compare product names, reachable UI actions, tool schemas, scope and returned fields with their current owners. Run `node scripts/check-bundled-guidance.mjs --source`, then check the extracted release packages and their `read_scientific_skill` receipts. Record reviewed and changed guidance, package checks and limits in the version document. Resolve guidance regressions before tagging. Follow the [release guidance checks](docs/development/windows-update-release.md#核对内置指导).

Compatibility policy: before 1.0, prioritize substantial improvements over preserving disposable development/test conversations. Document necessary breaking changes explicitly. Preserve SSH connections, credentials, registered compute environments, project authorization, and real run state unless the user explicitly requests otherwise. Starting with 1.0, require backward compatibility and versioned data migrations.

Regression policy: test the layers and behaviors actually changed, not the development version number. Frontend-only changes require affected component and native interaction checks, not backend or scientific reruns. Backend-only changes require affected API, state and persistence checks. Test both sides when a shared frontend/backend contract changes. Run bounded real scientific examples only when a change can affect engine execution or numerical results and the affected behavior cannot be established by contract tests; select only the affected routes. Full software or scientific matrices are reserved for an explicitly requested comprehensive acceptance, never automatically for each dev release or UI audit. Reuse unaffected evidence with its original source/version and scope; never relabel it as a new scientific run. For scientific checks that are actually needed, A keeps passed/failed/blocked/not_run evidence, uses isolated ignored runtime roots, preserves production jobs and sibling engines, and keeps private connection details out of tracked reports. The comprehensive native button audit and independent workflow-use counts remain separate from scientific regression.

Development review runbook: for explicitly authorized A/B/C review work, use [studio-development-loop](docs/development/skills/studio-development-loop/SKILL.md). This development skill is outside product scientific skill roots; it does not authorize delegation on unrelated tasks.
